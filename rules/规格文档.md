# 规格文档

> [!note] 同步维护
> 以知识库 `wiki/规格文档.md` 为维护入口；更新 Wiki 时，必须同步更新仓库中的 `rules/规格文档.md`，保持两份文档内容一致。项目初始化时复制 `rules/` 中的版本。

## 核心思想

**每个功能写一份说明：做什么、有哪些限制、怎样才算做好。你定要求，AI 写代码，最后按说明检查。**

这份说明就是“规格文档”，直接写成可交给 AI 的提示词。先预测结果，再实际运行，记下差别；代码以后可以重写，要求和检查记录都留在文档里，既能完成开发，也能积累经验。

## 详细说明

### 文档和代码旁的说明，分开放

- **文档**：记功能要求、限制和检查结论，方便以后重做或换项目使用。
- **代码注释**：写在代码旁，只解释附近代码；改代码时一起更新。

| 内容 | 放哪 |
|---|---|
| 做什么、需要什么、返回什么、有哪些限制 | “任务”“技术与边界”“功能要求” |
| 并发、数据一致性这类硬约束 | “数据与并发” |
| 怎样测试、性能和资源怎样算达标 | “测试与性能” |
| 容易出错的情况 → 预期结果 → 实际结果 | “预测 → 实测” |
| 交付方式和汇报要求 | “执行与交付” |
| 某几行代码为什么这样写 | 代码注释 |
| 临时草稿 | 有用的内容整理进文档 |

### 一份文档的标准格式

下面用“本地项目任务管理器”演示写法，**没有做过真实测试**。这本身就是一份可以直接发给 AI 的提示词：照这个结构，把内容换成你项目的实际要求，“待测”换成真实实测结果。

速度就是等多久能得到结果；资源就是用了多少电脑计算能力、内存、磁盘空间或钱。只写需要限制的项目。没有依据时，先测出当前水平，再确定要求，不随便填数字。

性能数字要写清测法，不能只写“快”。先用最小原型或空跑测一个基线，再留 2–3 倍余量。至少写：p95 还是平均值、多少并发、正式请求多少次、预热几次、跑几轮取哪一轮、机器和版本。换机器或换语言要重新测。压测客户端自身的实现也会明显影响测得的延迟：定阈值前，先用最小回显对照服务器跑同一负载，确认客户端开销远小于阈值；换了客户端实现，同一服务测出的数字不能直接比较。费用也要写清统计范围：只算模型调用，还是也算存储、带宽、人工。分别记“实付 / 估算 / 未测”；实付写金额来源，估算写模型、用量、单价和单价日期。没有数据就写“未测”，不能写成 0。下面示例的“测试与性能”一节演示了其中性能部分的写法。

```markdown
# 标准提示词格式

## 任务

在当前目录实现一个本地项目任务管理器。

## 技术与边界

- 后端使用 Python 3 标准库，数据库使用 SQLite。
- 前端使用原生 HTML、CSS、JavaScript。
- 服务只监听 127.0.0.1。
- 不使用外部服务，不安装第三方依赖。
- 只修改当前目录，不提交 Git。

## 功能要求

- 项目支持创建、查看和删除；项目仍有任务时，必须拒绝删除并说明原因。
- 项目下的任务支持创建、编辑和删除。
- 任务字段：
 - 所属项目：必须关联已存在的项目。
 - 标题：去除首尾空白后不能为空，最长 100 字符。
 - 描述：最长 2000 字符。
 - 状态：待办、进行中、已完成。
 - 截止日期：可以为空，填写时必须是有效日期。
- 网页功能：
 - 可以切换项目，将当前项目的任务按三个状态分列显示。
 - 可以通过按钮切换任务状态，无需拖拽。
 - 可以按标题关键词筛选任务。
 - 后端报错时，显示原因，并保留尚未保存的编辑内容。

## 数据与并发

- 重启服务后，所有项目和任务仍然存在。
- 所有数据校验和项目关联约束必须在后端执行，不能只靠网页检查。
- 每个任务包含版本号；更新或删除时，客户端必须提交读到的版本号。
- 版本过期时返回 HTTP 409，不得覆盖较新的修改。
- 版本检查与更新、删除必须是原子操作；两个请求使用同一版本更新同一任务，最多只能有一个成功。

## 测试与性能

- 使用 unittest 编写自动测试，启动真实本地 HTTP 服务，通过 HTTP 请求验证行为。
- 测试使用临时数据库，不得改动日常使用的数据库。
- 覆盖正常增删改查、无效输入、项目关联约束、重启后的数据保留，以及两个请求竞争更新同一任务的情况。
- 性能测试使用临时数据库，包含 100 个项目、10000 个任务，每个项目 100 个任务；数据准备、服务启动和预热不计入耗时。
- 通过真实本地 HTTP 请求测试项目列表、当前项目任务列表、标题筛选及任务增删改：5 个客户端并发，每类操作至少执行 100 次，每类操作的 P95 响应时间不超过 300 毫秒，单次不超过 1 秒。响应时间从客户端发出请求到完整收到响应计算。
- 性能测试使用有效输入；除专门测试版本冲突外，写请求操作不同任务。并发读写不得出现未处理异常或数据库锁错误；同一任务的竞争更新仍须遵守 HTTP 409 约定。
- 当前项目有 100 个任务时，任务列表渲染和标题筛选的页面更新时间不超过 200 毫秒，不含 HTTP 等待时间。
- 自动测试和后端性能检查分别支持一条命令运行，均不得引入第三方依赖。

## 预测 → 实测

- 测试前列出关键场景和预期结果，测试后补充实测结果；未测试的保留“待测”。
- 使用同一版本同时更新同一任务两次 → 预计一次成功，另一次返回 HTTP 409 → 实测：待测。
- 删除仍有任务的项目 → 预计拒绝删除并说明原因 → 实测：待测。
- 重启服务 → 预计所有项目和任务仍然存在 → 实测：待测。

## 执行与交付
- 先检查环境并给出分步计划，再直接实现。
- 分阶段运行检查；失败时先定位原因，再修改。
- README 写清启动、自动测试和性能检查命令、数据文件位置及 API 约定；记录性能测试环境、数据规模、并发数、样本数和实测结果。
- 最后区分已验证、未验证和已知限制。未操作过的网页功能、未实测的网页性能，必须标为未验证，不得声称测试通过。
```

写“预测 → 实测”时，每条尽量写成“什么情况 → 期望什么结果”，实测后补上真实结果，验收时才能判过不过。至少覆盖：重复/并发、边界值、非法输入、重启后数据还在不在、数据量变大。时间边界（正好过期、跨时区）和编码边界（中文、空格、已有 `%XX`）最容易漏。

### 怎么交给 AI 实现或重写

规格本身就是提示词，写好就能直接发给 AI。还没选定语言和工具时，可以先让 AI 给建议，再附上这段通用指令：

> 按这份规格，用【语言和工具】实现。守住功能要求、特殊情况和资源限制，其余做法自行选择。先保证正确，再解决速度和资源占用不达标的问题，直到所有检查通过。达到要求就结束，不额外增加功能或反复优化。遇到要求冲突或无法验证的地方，说明原因和还缺什么条件。
>
> 不许改规格里的功能、数字和验收条件；发现规格有问题，停下来列出来，不要自己补。做完报告：完成了什么、没做什么、做了哪些假设、证据在哪、和规格有没有偏差。状态先写“待验收”，不要自己写“已通过”。

以后换语言或工具，仍可使用这份说明，但要重新检查功能、速度和资源消耗，不能默认结果一样。

### 交给 AI 前，先自己检查

- 每条要求都能判“过/不过”吗？有没有“快、稳、友好、尽量”这类没法判的词？
- 每个数字都写了测法吗？p95 还是平均值、多少并发、跑几轮、在哪台机器上测。
- 费用写清范围了吗？只算模型调用还是也算存储、带宽；实付、估算、未测分开，缺数据不能写 0。
- 接口写清了吗？输入、输出、状态码、错误情况。
- 边界覆盖了吗？重复/并发、非法输入、边界值、重启、数据量变大、时间和编码。编码类的写清“原样保留”还是“解码后比较”。
- 时间相关的要求，能用短 TTL 等待或可替换时钟测吗？不要靠直接改数据库卡边界。靠等待过期的取样要保证取得到有效样本（例如等到整秒开始再建样本）；快速重试不跨秒，等于只抽一次签。
- 证据放哪、用什么命令跑，写了吗？
- 一份说明是不是只讲一个能独立验收的功能？混进两个就拆。

### 三条提醒

1. **一份说明只讲一个能独立验收的功能：一个明确目标，加一组能各自判过/不过的验收条件。** 篇幅跟着功能走，别为了凑一页删要求；接口多但共用一套约束（同一个数据库、同一组并发要求）时，可以留在一份里，用小节分开。接口数量不设硬上限，能不能拆按验收条件是否独立来判，保留人的判断。
2. **重要变化要更新说明。** 功能表现、限制或检查结论变了，文档一起改；只改局部代码细节，不必改规格。
3. **实现和验收分开。** 实现的人只拿冻结的规格和运行约束，最多把状态写成“待验收”；验收的人拿规格、证据和可运行产物（含启动说明），不读实现源码，按证据判“已通过”或“已废弃”。代码审查另做。隔离说明要如实写实现方实际拿到了什么；除规格和运行约束外还拿到材料（如既有测试脚手架）的，不算严格盲测。

## 文档放在哪里

放在项目的 `docs/specs/` 文件夹，和代码一起保存。`docs/index.md` 用来列出每份说明是做什么的。

```
项目文件夹/
├── src/                              # 代码
├── docs/                             # 文档
│   ├── index.md                      # 文档目录
│   ├── specs/                        # 功能说明
│   │   ├── 001-task-manager.md        # 任务管理器
│   │   ├── 002-user-auth.md           # 用户登录
│   │   └── 003-order-payment.md      # 订单付款
│   └── logs/                         # 验收证据
│       └── 001-task-manager/
│           └── 2026-10-24-verify.md
└── README.md                         # 项目介绍
```

文件名用 `编号-功能英文名.md`，不会起英文名可以让 AI 帮忙。**一个功能一份文档**，以后重写哪个功能，就取对应的说明。

上面的示例是发给 AI 的提示词正文；归档到 `docs/specs/` 时，在文件开头补上状态和更新时间，每次改动顺手更新日期。状态用“待实现 / 实现中 / 待验收 / 已通过 / 已废弃”，由验收的人改，不要由实现的人自己写“已通过”。验收证据放 `docs/logs/`，按功能分文件夹，文件名带日期，里面记环境、命令、输出和结论。
