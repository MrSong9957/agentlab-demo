# 模块灰盒法

任务分两步：第一步逐块想清楚、做出来、跑通，走最小路径；第二步统一查缺补漏，走完整路径。节奏和手写一样：先跑通，再打磨。唯一区别：模块内部的代码由 Agent 写。用户说清它做什么、进什么、出什么、出错怎么办。

## 1. 第一步：最小路径，逐块跑通

1. 想模块：做一块前，想清楚这一块叫什么、管什么、不管什么、进什么、返回什么、什么情况算错。用大白话写进对话，或写一份短说明。
2. 定接口：写下签名、参数、返回值、错误类型、可见性。Rust 里就是 `trait`、函数签名和 `pub` 边界。接口由用户写，或写完由用户确认；Agent 不得定接口。
3. 写验收：写这块跑通要用的测试：正常情况下模块外面能看出什么行为。测试先红着（失败）。
4. 交实现：一次只给 Agent 一个模块，让它只填内部实现，不交整个项目。交代三条：不得改签名、不得改测试、不得为跑通加绕路。Agent 发现按接口写不下去时，停下告诉用户，不得糊过去。
5. 跑通：编译过、正常场景测试过，Agent 附命令和输出作证据。模块经用户验收，再做下一块。全部块完成，第一步候选版本交用户验收。

第一步中发现计划没列的边界或异常：记下并报告，不在第一步处理，作为第二步增量规格的输入。

## 2. 第二步：完整路径，查缺补漏

6. 写增量规格：把第二步的规格作为增量写在同一份规格文档后面：实现暴露和讨论确认的边界、异常条目，加第二步验收条目。经用户确认后，把场景补进计划并再次确认。
7. 查缺补漏：按计划写边界、异常等测试：单元、集成、E2E，走完整路径，comprehensive-testing 在功能级汇总。测试先红着（暴露缺口），Agent 只补模块内部实现到通过，不得改接口和已有测试。发现增量规格没列的边界或异常，停下告诉用户，由用户定补不补。
8. 自己验：用户自己跑编译和全部测试，不采信 Agent 的「通过了」。再核对接口没被动过。全量验证后，用户验收最终候选版本。

## 3. 长结构

做完一块加一块，层级结构由用户一步步搭出来。哪一步发现前面某块接口定错，回头改那一块再往下走，和手写时一样。

## 4. 底线

模块内部可以是黑盒：用户可以不看，出问题时再读源码。接口和层级结构不能是黑盒，这两样一直在用户手里。

## 5. 适用场景

| 场景 | 做法 |
|---|---|
| 长期维护、要给别人看、涉及安全数据的项目 | 用本方法 |
| 一次性脚本、随手试的原型 | 直接让 Agent 写，不用这套 |
| 想学某个东西的原理 | 用户自己手写 |
