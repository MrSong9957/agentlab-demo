## 1. 目标 & I/O

补齐两条相连的链路，作为同一功能交付：

1. **模型发出重要消息 → 用户立即看到 → 工具确认受理 → 继续当前任务**。
2. **用户在任务运行中追问或回复 → 普通用户消息进入当前任务 → 模型回应后继续工作**。

第二条使用 Codex 的普通输入接续（steer）语义，不增加另一项模型工具。只打印消息而把所有中途追问留到下一轮，不能算完成本计划。

### 1.1 工具接口

```json
{"message":"发现现有配置与规格不一致，我会先核对来源，再继续修改。"}
```

- 工具名固定为 `send_message_to_user_async`；唯一必填字段为字符串 `message`，拒绝未知字段。
- 沿用 Codex 的 `trim()`：去掉首尾空白，保留内部换行与原文；空字符串、全空白报 `message must not be empty`。非法 JSON、缺字段、`null`、错误类型均报参数错误，不显示成功消息。
- 沿用上游 Schema 的 `additionalProperties:false` 与 `strict:false`，映射到本项目 Chat Completions function 封装。参数只有文本，不增加标题、重要性等级、超时或收件人。
- 成功结果严格为 `{"accepted":true}`，不附加消息 ID、回答、`ok` 或等待句柄。错误使用本地既有 `{"error":"具体原因"}`；这是错误封装适配，不改成功结构。
- `accepted` 只确认参数有效并由本地发送路径受理；不代表用户已读、已答、任务完成或落盘必定成功。沿用现有落盘告警，不承诺跨崩溃的投递恰一次。

用途按 Codex 工具描述确定：重要阻碍、可能改变任务方向的发现，以及任务运行中的追问或状态请求。上游也允许在自由文本中提出需要注意的问题；它不因此创建结构化问询或等待。日常进度沿用已有计划和工具活动展示，不把所有进度都升级成重要消息。

### 1.2 开放范围

Codex 在根线程且“功能开关开启 **或** 模型目录显式声明支持”时注册该工具，默认功能开关关闭。本地首版采用其**模型目录声明**这一路，不为一个工具引入整套上游 feature 系统。

- 在现有 `catalog::ModelInfo` 中增加可选 `experimental_supported_tools` 字符串数组；按现有逐字段覆盖规则合并。模型对象示例：

```json
{
  "id":"example-model",
  "experimental_supported_tools":["send_message_to_user_async"]
}
```

- 缺省或空数组不启用；只按精确工具名判断，不根据模型名称、同步问询或异步问询能力推断。数组中的其他名称不自动获得本地执行权限，也不注册未知工具。
- 手动值覆盖自动目录值；显式空数组可关闭目录声明，未写字段不覆盖已有值。`/refresh` 保留手动覆盖；不新增在线能力探测。
- 普通用户轮、带记忆摘要的用户轮，在当前模型声明支持且宿主具备消息输出路径时各增加一项工具。TUI、行式 CLI、非交互管道都可输出消息；管道不因此获得实时回答通道。
- 内部 `MemoryMerge` 不声明、不执行该工具；没有消息宿主的底层调用方默认关闭。声明与执行分派共用同一轮能力快照，伪造调用不能绕过关闭状态。
- 不把通知能力绑定到 `request_user_input_async`、F6 或未决问询槽位。本项目没有子 Agent；若将来接入，继续遵守上游仅根线程的限制，本次不建设多 Agent 框架。

## 2. 边界 & 风险

### 2.1 消息生命周期与用户看到的结果

| 事件或状态 | 采用的行为 |
|---|---|
| 合法调用成功 | 按调用顺序显示一条完整 assistant Markdown 消息，再继续同批后续工具及下一次模型请求；不等待用户 |
| 上游消息标记 | `id=call_id`、`phase=FinalAnswer`、`delivery=Async`、`questions=None`；其中 FinalAnswer 是消息元数据，不等于 TurnComplete |
| 本地显示 | 复用 assistant Markdown cell，独立保留在对话中；不作为 Info、命令执行卡片、问询卡片或本轮最终回复 |
| TUI 正在输入 | 不抢焦点、不清空草稿、不打开回答窗口；任务运行状态和取消入口保持可用 |
| 多条消息 | 每个成功调用显示一条；不同调用 ID 的相同文字仍分别保留，不新增按正文合并或节流 |
| 参数失败、关闭态伪造调用 | 返回工具错误，无成功消息；失败结果保留，可继续既有工具循环 |
| 取消发生在调用前 | 按原取消契约补未执行结果，不显示该消息 |
| 已受理后取消或后续工具失败 | 已发生消息与结果保留，不撤回，也不改写成任务完成 |
| 第 8 次请求返回通知 | 与其他合法工具一样执行并记录，随后报原请求上限；不发第 9 次请求 |
| 任务真正结束 | 只由原最终回复／失败／取消通路结束 turn；通知不触发完成响铃或桌面提醒 |

本地通过现有 `TurnNotify::ToolEnd` 的成功结果投影成消息项，避免同时发送另一套重复正文事件。只补必要的 `HostHistoryItem`／驱动处理，使该消息追加时不调用 `DriverEvent::Final`、不清理 streaming 状态、不置 `turn_running=false`。成功通知的工具活动行不重复打印正文；失败仍明确显示原因。

显示前复用 `display::sanitize_for_terminal`，只过滤展示副本；调用参数及后续模型看到的历史保留原值。文本中的命令、路径和链接只是正文，不新增执行、自动打开或权限授予。

### 2.2 模型历史、保存与恢复

Codex 的测试明确要求：工具消息发出后，下一请求含调用与 `{"accepted":true}`，**不额外插入同文 assistant 消息**。本地采用同一边界：

- 继续保存 V1 `AssistantToolCalls` 与配对 `ToolResult`；通知结果不需要新增持久化枚举、字段、数据库或文件，`display/image` 为空。
- 通知正文已在调用的 `arguments.message` 中；不再写一条 `HistoryItem::Text`。请求投影、记忆提炼也不人为补一条同文 assistant 消息。
- 实时成功结果与 `/resume` 共用“工具名匹配＋参数可解析＋结果明确 `accepted=true`”的转换，重建一条 assistant 消息。未知、缺失、取消、失败或损坏结果不能推定发送成功。
- 恢复只展示，不重新调用、不重新发出通知事件。007 对悬空调用的“可能已执行，结果未知”语义保持，不把未知结果说成未发送。
- 新程序读旧会话不变；旧程序能保留原有调用与结果，但显示为一般工具记录，不能承诺旧界面具有新消息样式。
- 模型原响应本来携带的 `assistant.content` 仍按 006 原样保存；“不额外插入”只限制本工具派生的消息，不删除模型原始正文。

### 2.3 运行中追问与回复：普通输入接续

Codex 的消息处理器不收集回答；后续回复由已有 `start_or_steer_turn`／输入队列接收，在下一次模型请求前进入历史。本地当前同步循环缺少这条入口，须作以下最小适配：

1. **保留两种输入意图。** TUI 普通任务已进入可接续状态时，Enter 提交尝试送入当前轮；显式排队键（沿用当前 queue key）仍留待后续轮。普通消息不需要关联先前通知的调用 ID，也不要求先收到一条通知才可中途追问。steer 与通知工具开关相互独立，与 Codex 一致。
2. **复用 020 完整消息。** 输入框、暂存、宿主和回执都携带 `SubmittedTurn` 的文字、附件路径及 `TextElement`，不得退回 `String`。图片准备复用现有核心、能力快照、限制及失败恢复；正式接入历史前才读取／准备，不因排队提前冻结全部图片。
3. **独立于历史锁。** 使用每轮独立的输入通道／短锁暂存状态；提交侧不获取 turn 长时间持有的 `history` 或自动保存锁。以宿主生成的轮次与提交标识关联，保证只有当前普通用户轮可接收，不启动第二条并发模型调用链。
4. **固定入史边界。** 先完成本次已返回的完整工具批及所有结果配对，再接入已准备的普通输入，随后组装下一请求；不能在 assistant 调用和 tool 结果之间插 user。通知可先显示，用户输入最早在下一请求生效，不中止已经开始的命令或声称在途请求已经看见新输入。
5. **处理终文竞态。** 模型返回纯文本时，若当前轮已受理的待接续输入尚未处理，不提前宣告任务完成；保留该正文并继续，让模型先处理新输入。收取输入与封闭当前轮需在同一接续状态上原子判定；迟到输入得到明确“当前轮已结束”回执，再进入后续轮，不能丢失或同时走两条路径。
6. **区分暂存和入史。** 每份输入只在正式入史时确认提交，按受理顺序恰一次保存／回显。准备中、等待接入和显式排队要有准确预览；取消、错误或额度耗尽时，未入史输入按 020 规则保留／恢复为待处理完整消息并暂停自动发送，已入史消息保留且不自动重发。用户后来写的草稿不可被旧回执覆盖。

本地 HTTP 等待与命令执行仍采用现有同步边界，不为本功能移植 WebSocket、请求抢占、通用任务调度或整套 App Server。接续消息沿用当前任务剩余的 8 次模型请求额度，不重置计数；准备和等待输入不额外请求模型。没有输入时照常工作，绝不为等待一条可能的回复而阻塞通知工具。

这项行为**有意修订** 008／020 中“运行中 Enter 一律排到下一轮”的契约；实施时同步更新对应条目和有意变化的回归期望。显式排队、准备失败恢复、图片入史与按键单一职责仍由原契约约束，不能借此放宽断言。

### 2.4 与结构化问询、CLI 的关系

- 018 的同步问询、异步问询和 `wait_for_user_input` 保留独立回答通道；新通知不占用“单项未决”槽位，不生成 `UserInputEvent::Answer` 或 `Closed`。
- 问询窗口中的提交仍回答当前问询；普通 composer 输入才走 steer。普通消息不自动消耗未决结构化问题，F6 保持只负责问询窗口。
- `wait_for_user_input` 已经阻塞时，普通消息不冒充所等答案、不虚构就绪。新普通输入保留，待专用回答到达、等待结束并完成工具批后再接入；Esc／退出仍可结束等待。这是既有本地等待工具的边界，Codex 通知处理器本身没有该等待工具。
- 同批若有结构化答案与普通输入到达，两者均在完整工具结果之后入史，保留各自来源与次序，恰一次投影；测试固定实际受理顺序，不依赖线程时序猜测。
- 行式 CLI／管道必须能在终文前输出并 flush 通知，继续执行后续工具；本地行式宿主运行 turn 时没有第二个终端读取者，因此不声称支持 TUI 的运行中键盘接续，也不另起线程抢读 stdin。后续行仍按原普通输入方式处理。
- 通知以及普通回复均不授予执行权限；退出、取消、命令和会话切换仍经过已有入口。

### 3.3 执行顺序

1. **确认基线并写 RED → 验证缺口可检出。** 记录相关原有用例状态；先补非法输入与工具真实循环用例，再补消息未结束任务、运行中追问接续及终文竞态的失败用例。
2. **接通单向消息 → 验证消息先出现且工作继续。** 实现能力声明、严格解析、accepted、CLI／TUI 展示和恢复；用受控下一响应证明通知出现时后续工作仍在执行，而非完成后补打印。
3. **接通普通输入接续 → 验证当轮生效与完整数据。** 以独立通道、批末入史和回执打通 Enter；保留显式排队；覆盖附件准备、晚到回执、取消、结束及 018 同时问询。
4. **完成全链路验收 → 验证真实用户结果。** 真实 CLI＋PTY 屏幕、HTTP 请求、历史与文件副作用交叉核对；通过后按项目门禁加固、审查和最终全量验证。

前两步完成不等于本功能交付；第 3 步与验收清单同样属于本计划完成条件。实施授权、提交／合并等后续动作不由本计划文档代替。

## 4. 坑记录

- 上游通知带 `FinalAnswer`，但事件是 ItemStarted／ItemCompleted，并非 TurnComplete；不能复用本地 Final 事件图省事。
- 上游测试明确禁止把通知再作为 assistant 正文加入模型上下文；界面有一条消息，不等于必须多写一条模型历史。

### 5.3 测试质量与门禁

- 单元与集成使用固定模型响应、固定输入和独立临时目录，覆盖配置／用户目录环境变量；不使用真实密钥或在线模型，不污染真实配置。竞态以通道和显式检查点控制，编号用确定性计数，不靠随机数或当前时间决定断言。
- 稳定 JSON、文本与屏幕优先用黄金值／既有快照；同时检查请求数量、工具执行路径、文件副作用、轮次与历史配对，不能只匹配一行“发送成功”。
- 关键用例保持断言不变，通过 RED／GREEN 或隔离副本可逆变异证明至少能发现：通知被当 Final、移除 trim／空白拒绝、删除实际消息输出、额外注入 assistant 正文、Enter 仍排下一轮、批中插 user、终文忽略已接收输入、接续漏附件。恢复原始字节并核对哈希，不直接接受错误快照。
- 计划用例全绿后依次执行 `comprehensive-testing → Security Testing → code-review → 全量验证和修复`。加固重点是接续状态与结束竞态；安全测试聚焦输入来源、跨轮回执、工具隔离、终端过滤及既有权限。任一阶段出错，使用 `diagnosing-bugs` 定位根因，修复后复验受影响项并完成最终全量。
- 默认回归仍由 `/workspace` 的 `cargo check && cargo test --workspace --no-fail-fast` 一条命令覆盖，关键 CLI／PTY 场景纳入 `e2e_acceptance`。单例过滤只用于排查，不能作为交付依据；按实际工具链执行适用 lint，报告通过、失败、忽略／跳过、过滤和未运行数量。
- 若使用独立工作树或副本，两个 Cargo 命令都显式 `--target-dir` 指向该副本专用目录。V1 与配置兼容通过固定夹具和往返行为验证，本项目没有已采用的公开 crate API 兼容工具，不额外强加。
- Linux PTY 能证明本环境界面与输入行为；Windows ConPTY 或宿主终端效果没有实际条件时如实列为未运行，不把模拟屏幕视为真实宿主验证。
