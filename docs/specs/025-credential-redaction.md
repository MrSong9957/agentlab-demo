## 1. 要做什么，有哪些要求

- 目标 1：上述 artifact 的明文值替换为占位符（如 `[REDACTED-2026-10-26]`），保留 JSON 结构与 `kind`/`toolName`/`toolCallId`/`createdAt`/`files[].path` 追溯字段不变。
- 目标 2：替换用一次性脚本在 shell 内完成（`python3 -I`），不经任何会留存文件快照的工具；脚本与命令行不包含、不打印被替换值（按形态匹配，不从 `.env` 取值）。
- 目标 3：替换后对 `~/.zcode` 全目录复扫 `sk-[a-f0-9]{32}` 与 `ghp_[A-Za-z0-9]{36,}` 形态，明文计数为 0；同时确认 `/workspace/.env` 字节内容与替换前一致（仅报告布尔，不输出内容或哈希）。
- 目标 4：代码侧脱敏覆盖核实——既有机制（`api.rs` 错误脱敏与截断顺序、`mcp/secrets.rs` 污染拒绝、`display.rs` 终端净化、`git-token-check.sh`）覆盖的出口逐项对照；仅修复已证实缺口，无缺口则记录核实结论、不重构。

## 2. 哪些情况容易出错

- 用 Agent 的 Edit 工具改 artifact → 该工具或同类工具可能再次留存改前快照 → 必须用 shell 一次性脚本。
- 脚本把值写进命令行参数或打印差异 → 明文进入会话记录 → 脚本只按正则形态就地替换、只输出计数。
- 替换破坏 JSON 结构 → ZCode 无法解析历史 → 替换后 `jq` 校验追溯字段仍可读。
- 只处理已知一个文件而形态扫描另有残留 → 处理后必须全目录复扫，不依赖处理前的定位结论。
- 把"核实无缺口"做成大范围重构 → 违背最小修改；仅已证实缺口才补。

## 3. 重要做法，为什么这样做

- 形态匹配而非取 `.env` 值比对：脱敏动作本身不接触当前真实值，避免新的暴露面。
- 保留追溯字段：历史记录仍能回答"何时哪个会话编辑了哪个文件"，只去值不去据。
- 布尔／计数验收：所有验证输出不含值、不含哈希，与既有 `git-token-check.sh` 脱敏管道约定一致。
