## 1. 要做什么，有哪些要求

### 1.1 目标与首版范围

让模型申请**当前用户轮内**额外的本地文件读写或网络权限，用户在专用界面明确允许后，后续执行确实按批准范围运行；拒绝、取消、超出管理员上限或环境不支持时不扩大权限。

权限申请、确认界面、强制执行和到期收尾属于同一项任务，不能只实现一个返回“已批准”的工具。首版只做 Linux，在 033 的 `sandbox.rs` 统一启动模块内补齐可信策略、受限读取、网络与系统调用限制；优先复用固定版本上游的成熟实现，不恢复已删除的双账号降权链路。其他系统不宣称等价实现。

- 申请工具通过普通函数适配 024 的五协议，不依赖厂商托管审批；与 030 工具搜索互不依赖，权限工具始终直接声明，不进入延迟工具目录。
- 仅支持实际路径的 read/write 和网络启用；不支持会话级/永久授权、root/sudo 提权、切换到应用凭证身份、任意执行器、环境 ID、shell 前缀规则、域名白名单或自动审阅者。
- `network.enabled=true` 表示本轮本地命令的广泛 IP 网络访问，可能包含外网、宿主/局域网以及监听端口，仍受 OS 限制；不能把它描述成“只访问某网站”。MCP/模型服务的认证和远端业务权限仍由原有配置与服务自身控制。

### 1.2 当前事实与启用前提

033 已替代 027 B 双账号链路并交付本地 main；共享 dev 已部署并默认启用 `TCHAT_SANDBOX=1`，见[部署记录](../logs/033-tool-sandbox/2026-10-27-dev-deploy.md)。命令、MCP stdio 与补丁共用 `sandbox::tool_launch_argv`：全盘只读、工作区及系统临时目录可写、工作区 `.env` 遮蔽，网络保留；PID/用户/IPC 命名空间与新 `/proc` 已接通。模型指定 workdir 只改变执行位置，不改变锚定主进程 cwd 的固定策略。

**033 还不是动态权限后端**：`SandboxPolicy` 为内部固定策略，`full_disk_read=false` 明确报错，未实现读取白名单、按授权生成策略、网络开关及应用层 seccomp/no_new_privs。Docker 的 seccomp 放行配置用于允许 bubblewrap 建立沙箱，不能当作每个工具的网络或系统调用策略；`view_image` 仍走 019 宿主读取入口。TUI 权限展示占位也不代表已有授权、执行与撤销能力。

新增可信启动变量 `TCHAT_PERMISSION_POLICY=<绝对策略路径>`：

1. 未设置时保留现有普通模式及 `TCHAT_SANDBOX` 的 033 行为，不声明本工具，即使模型目录包含工具名也不能伪造调用。不得因新增功能悄悄收紧或放宽旧模式。
2. 设置时进入 031 模式，且必须已启用 `TCHAT_SANDBOX`；启动加载策略，检查可信应用/bubblewrap 安装及 031 扩展后端，验证实际内核隔离能力和永久边界。缺开关、后端不完整或策略不可执行时启动明确失败，不能退回普通 shell、033 的固定全盘可读/网络开启策略或“只靠提示词限制”。
3. 031 模式启用后，所有本地模型控制的执行/读取均受基线约束；不能把强制约束仅放在已申请过权限的路径上。模型目录是否支持申请，只决定能否出现申请入口，不决定是否执行基线限制。
4. 只有 031 后端可用、当前是普通用户轮、模型 `experimental_supported_tools` 精确包含 `"request_permissions"` 且有专用交互宿主时才声明并执行申请。非交互管道、无确认宿主或内部记忆轮没有入口，不自动许可。
5. 033 的独立宿主验收与共享 dev 部署可证明其已实现范围；不能据此填写 031 动态策略的实测结果。M0 必须在实际目标容器重新验证新增限制、允许正例和到期收尾；缺少可用环境属于部署与验收缺口，不标功能通过。

### 1.3 可信策略与永久边界

策略由应用在启动时读取并固定；文件及父目录必须位于模型工具不可写的可信部署位置，不能来自 cwd 项目配置、模型参数或 `.env`。新变量加入 `TRUST_CONTROL_VARS`，`.env` 不得启用、关闭或改换策略。包含内部执行入口的应用二进制、bwrap、必要的后端依赖和构建清单同样来自固定的不可写安装位置，不通过工作目录或模型 PATH 查找；031 模式不从可被模型覆盖的工作区产物自再执行。033 当前的工作区外 PATH 探测不足以替代本项固定安装位置与来源检查。

策略格式首版固定 `version=1`，包含：

- `base`：普通本地工具的基线 read/write 路径和网络布尔值。除固定后端提供且验证过的只读运行环境、沙箱私有临时目录外，不隐式开放用户目录或整个宿主根；不能继承 033 的全盘可读及共享系统临时目录写面作为隐式授权。
- `requestable`：管理员允许申请的路径与最高访问级别、是否允许申请网络。申请只能取此上限的子集，不能借 UI 改策略。
- `deny_paths`：额外的永久拒绝路径。应用还必须自动合并 `.env`、应用凭证/配置/会话/记忆私有根、策略与应用/bwrap 安装目录、宿主控制套接字等安全边界；用户批准祖先目录也不能冲掉更窄的拒绝。

033 与主进程使用相同宿主 UID，旧方案关于不同 UID/属主防止敏感硬链接读取的前提已经失效。031 仍须守住该边界：M0 用敏感假文件的预存硬链接、bind 别名及可写目录替换证明其在获批树中仍不可达，同时核验私有 `/proc`、fd 与控制套接字。仅遮蔽原路径不合格；须选定可证明边界的成熟挂载/部署方案，无法落实时拒绝启用 031 并保留缺口，不删除该验收要求、不恢复已删除的 027 链路。

所有策略路径为已存在的绝对实际路径，read/write 规则必须可被后端表达；不支持通配符、URI、`~`、变量展开或隐式创建目标。同一路径互相矛盾的重复规则、重复 JSON 键、未知字段、未知版本、不可执行的规则、可写策略来源均报错，不默默忽略；允许祖先与更窄永久拒绝的组合按上述拒绝优先处理，不算配置冲突。

策略结构示例（路径仅为部署示例，不表示本轮已配置或获准）：

```json
{
  "version": 1,
  "base": {
    "file_system": {"entries": [{"path": {"type": "path", "path": "/workspace"}, "access": "write"}]},
    "network": {"enabled": false}
  },
  "requestable": {
    "file_system": {"entries": [{"path": {"type": "path", "path": "/vault/export"}, "access": "write"}]},
    "network": {"enabled": true}
  },
  "deny_paths": ["/workspace/.env"]
}
```

`/vault/export` 在此例中须事先存在。策略不修改宿主文件属主/ACL、不替用户更改 sudoers；具体部署材料由实施方准备供管理员审阅。033 已部署不能替代 031 的可信安装、动态后端与别名防护验收。

### 1.4 工具输入与路径含义

工具名 `request_permissions`，唯一必填对象 `permissions`，可选字符串 `reason`；所有层级拒绝未知字段。

| 字段 | 规则 |
|---|---|
| `reason` | 可省略；提供时为非空字符串，最多 4096 UTF-8 字节，作为未信任说明展示；不是待执行命令或授权凭据 |
| `permissions.file_system.entries` | 可选；有值时为 1–32 项数组，每项恰为 `path` 与 `access` |
| `entries[].path` | 恰为 `{"type":"path","path":"实际路径"}`；路径字符串非空、最多 4096 UTF-8 字节，拒绝 NUL/ASCII 控制字符；中文、空格及字面的 `%XX` 原样处理 |
| `entries[].access` | 只能是 `read` 或 `write`；write 包含读取及该路径内文件变更能力；目录授权递归，但永久拒绝项继续生效 |
| `permissions.network` | 可选；有值时恰为 `{"enabled":true}`，只申请开启，不以 false/null/其他字段隐式撤销或扩大权限 |

输入至少有一项实际权限；整个 arguments 原始 JSON 最多 64 KiB。`environment_id`、scope、任意 token、旧版 `read/write` 数组、deny/unrestricted、额外执行用户及自动批准参数均不接受。

相对路径基于当前会话 cwd 解析，不能基于上一条 shell 内的 `cd`。逐组件解析并拒绝符号链接及不存在的目标，展示并批准规范化的绝对路径；不做 URL 解码、Unicode 归一化或环境展开。缺失的输出目录应另行申请已存在父目录，宿主不得自动把请求扩大到父目录。

用实际路径包含关系判断覆盖，不能用字符串前缀，例如 `/data/a` 不授权 `/data/ab`。重复项规范化去重，同一路径 write 覆盖 read；永久拒绝、管理员上限与现有 OS 权限优先。任何请求项非法或超出上限，整次失败且不弹确认，不暗中丢项后假装批准原请求。

请求示例：

```json
{
  "reason": "需要将本次导出文件写入已有的 /vault/export。",
  "permissions": {
    "file_system": {
      "entries": [{"path": {"type": "path", "path": "/vault/export"}, "access": "write"}]
    }
  }
}
```

### 1.5 确认与结果

- 确认界面由宿主生成，显示会话 cwd、规范化路径及 read/write、网络的实际含义、永久拒绝仍有效和“仅当前用户轮”；模型 reason 单独标为说明，不能覆盖宿主文字。
- 首版只提供「拒绝」与「本轮允许」，默认拒绝，无自动空答/超时批准；不开放会话授权、任意路径编辑或自由文本授权。全允许/全拒绝是上游“批准请求子集”的本地收窄，不能把一部分允许解释成全部允许。
- 复用 018 的唯一终端输入者及可取消专用回答通道，但使用独立的 typed PermissionHost/Allow/Deny 结果。普通聊天、排队消息、AGENTS.md、MCP 结果、request_user_input 回答或模型伪造的“用户已同意”都不能授予权限。
- 宿主内部绑定请求序号、对话代数及本轮 ID；只接受当前活动请求的回执，关窗后迟到/重复/旧会话回执丢弃。一个宿主同一时刻只允许一个权限确认，不能从终端输出注入回答。
- Esc/拒绝按钮只拒绝本次申请；取消本轮或退出按现有 010/012/018 键位与职责执行，不新增按键的第二职责。EOF/宿主关闭结束等待并清理本轮，不伪造允许。
- 已被基线或当前有效授权完全覆盖的合法请求直接返回 granted，不重复问；新增部分必须重新确认。拒绝或单次参数错误不清除此前有效授权；用户取消整轮才收回本轮全部额外授权。

结果固定四字段 `status / permissions / scope / error`：

| 情况 | 结果 |
|---|---|
| 用户允许且后端可表达，或本来已覆盖 | `status="granted"`；permissions 为本次实际规范化、完整覆盖的请求；scope 固定 `"turn"`，error=null |
| 用户明确拒绝 | `status="denied"`；permissions={}；scope="turn"，error=null；不扩大当前授权 |
| 参数/策略/后端错误或取消、宿主断开 | `status="error"`；permissions={}；scope="turn"，error 为脱敏原因；不发布新授权 |

成功示例：

```json
{
  "status": "granted",
  "permissions": {"file_system": {"entries": [{"path": {"type": "path", "path": "/vault/export"}, "access": "write"}]}},
  "scope": "turn",
  "error": null
}
```

结果不包含可由模型重放的权限令牌。错误或拒绝不宣称 OS 权限已经改变；granted 也不保证业务操作成功，宿主 OS 仍可拒绝访问。内部记忆轮的伪造调用继续按原未知工具契约拒绝。

### 1.6 后端强制执行与接入面

在 `src/app/src/sandbox.rs` 内扩展可信策略启动入口，由宿主把已校验的基线与本轮 grant 编码为内部策略快照；入口名称和类型在 M0 冻结，当前 `tool_launch_argv(command)` 还没有动态策略参数。保留其普通/033 默认行为，由同一模块维护挂载、探测、环境和失败语义，不新增平行包装器。优先沿 033 已固定的上游来源补齐成熟策略构造及过滤实现，不把整个上游 workspace 加成本项目依赖，不手写新的沙箱内核。应用/bwrap、必要依赖的版本、SHA-256、目标平台、适配补丁和许可证须可追溯，不采用未经固定的 PATH/最新版二进制。

- 同宿主 UID 下以实际挂载、命名空间、fd 和控制面证明隔离；不能用 user namespace 内显示的 uid 0 或不同用户名代替验证。主进程 cwd 保持稳定，模型 workdir 不能重新锚定策略；031 的可信策略锚点只由宿主固定。
- 限制必须覆盖 shell 子孙、文件系统/用户/PID/IPC 视图、网络和关键系统调用。复用 033 的独立会话、cap-drop、fresh `/proc` 与父死亡机制；新增受限读树、拒绝优先的挂载布局、网络关闭（如成熟后端的 `--unshare-net`）、no_new_privs/seccomp 在 M0 验证并冻结。不能把这些待补能力写成 033 已实现，也不能将 Docker 放行 profile 当作它们的替代品。
- 可信工具入口须逐启动确认策略构建成功且 `/proc` 与 PID namespace 匹配，隔离创建失败必须在模型命令执行前拒绝；不能保留宿主旧 proc 视图或只凭启动时一次探测判定。033 当前拒绝的受限读和 deny 祖先/可写后代组合须补齐可验证实现，其他不能表达的策略也不得静默降级。
- 环境清空后只注入已声明的必要非敏感运行变量；不继承应用凭证、主进程 fd、宿主控制 socket 或授权通道。MCP 显式配置的环境凭证仍沿 022，只交给其配置服务器，不流入 shell。
- 路径批准对象与实际挂载/读写对象须绑定；读前验证、路径组件及沙箱构建的替换窗口都需要真实竞态证据。只做 `starts_with`、canonicalize 或返回“approved”不足以作为执行边界。

| 操作面 | 031 模式中的执行方式 |
|---|---|
| exec_command | 使用启动时“基线＋当前有效授权”的完整沙箱快照；cmd/workdir/超时/PTY/输出参数不新增提权字段；模型原命令只有在沙箱就绪后才执行 |
| write_stdin | 继续操作原进程，不扩大其出生时权限；对旧基线 shell 发送命令不能获得后来批准的新权限；需额外权限应另起 exec |
| apply_patch | 沿 033 的 `apply_patch_sandboxed` 与 `--internal-apply` 接入同一策略启动模块；源读取、判型、生成与写入均在沙箱内，主进程不得代读模型路径；结果/部分成功继续遵守 004，未来 Move 同样受源/目标权限限制 |
| view_image | 033 尚未覆盖；本项新增受控内部图片准备入口，把模型指定路径的打开和读取移入同一沙箱；主进程只接收有界编码图片及既有摘要，不因格式门存在而先读取越权文件 |
| MCP stdio | 初始化时按可信基线进入同类沙箱，保持已有显式 env/stdio 语义；复用连接不继承本轮临时授权、不自动重启或重放。需更宽长期范围由管理员改基线并重启 |
| 模型 API 与 MCP HTTP | 已配置的控制面连接不受本地 shell 的临时网络开关影响；不从模型请求权限字段改服务器 URL/认证/名单，远端业务权限不因本次授权扩大 |
| 用户主动附件、应用配置/上下文/会话/记忆 | 保持各自既有宿主边界，不能由模型权限工具伪装成用户附加文件或读取应用私有数据的通道 |

### 1.7 生效、到期及进程收尾

1. 只有匹配当前回执的“本轮允许”经验证并提交后，才更新本轮内存授权集合；不写持久化许可。单次允许全部生效或全部失败，累计去重后的额外路径最多 64 条，超限在确认前失败。提交 granted 前须完成生效策略的编码、后端可表达性及启动 argv/IPC 容量校验；失败不发布这次新增许可。
2. 申请本身不执行被拒过的命令，也不自动重试。后续工具（包括同批中排在申请之后的执行）在开始时取已批准快照；申请之前已经运行的进程不升级权限。
3. 继续 006 的批次先完整校验后串行执行、每轮 8 次模型请求、每批 32 调用和原 ID/name；询问期间不额外调用模型，第 8 次响应也要保存完整工具结果，不发送第 9 次请求。
4. 每个使用了额外权限的进程和后代绑定当前轮授权代数。正常完成、取消、模型错误、额度耗尽、成功的会话切换或退出，均须先终止并回收这部分进程，再结束本轮。不能只删内存记录而让其继续联网/写文件。被拒绝或失败的切换没有结束当前轮，不误清理当前授权或更换回执归属。
5. 这是对 016 的明确、有条件修订：仅 031 模式中以额外权限快照启动的进程不跨用户轮存活；只有基线权限的进程仍遵守 016 的可续接与取消保活。模型和界面必须能区分这两类进程。
6. 到期的活进程终态使用现有 terminated，并保留可查询的终态/输出；不增加结果枚举，不把早先历史中的 running 改成当时已经结束。宿主展示权限到期导致的终止；新用户轮不能用旧句柄继续输入或恢复权限。
7. 先统一发终止信号，再按 016 的 3 秒有界收尾窗口等待所有额外权限沙箱（不能每项串行等 3 秒）；父进程死亡路径也须清理整棵沙箱进程树。无法证实全部已终止时报告收尾失败、拒绝开始下一轮，不宣称已安全撤销。

### 1.8 保存、界面与资源条件

- 仅保存普通 AssistantToolCalls/ToolResult 及最终决定；活动授权、可信回执通道、目录 fd 与审批状态不入会话。五协议沿 024 保留原生块/签名。
- `/resume` 展示历史申请、允许/拒绝/错误和 turn 范围，不打开确认窗、不执行工具、不重建授权。新轮授权集合为空，历史里即使有 granted JSON 也不是当前许可。
- CLI 复用唯一输入者；TUI 复用现有选择/滚动/可取消通道的界面构件，但新增专用权限事件，不把一般问询答案转成授权。默认拒绝且已有草稿/排队消息不提交为批准；显示完整权限项目，路径作为转义后的数据呈现，显示过滤不能扩大或更换实际路径。
- 参数 64 KiB、reason/path 各 4096 字节、单请求 32 项、额外有效路径 64 条、策略文件 1 MiB 是本项新增的静态边界；均按 UTF-8 原始/完整 JSON 的上述定义计量，恰好允许、超过拒绝，不截断请求/策略后批准。
- 现有 128 工具声明、10 MiB 实际模型请求、补丁/图片/进程输出及会话限额继续适用；沙箱附加 IPC 必须复用相应结果的有界读取，不能把内部入口当作无限数据通道。
- 人的等待不设置自动允许时限。M0 记录当前机器/内核、应用与策略后端、bwrap、宿主 UID 和挂载；用假文件/假凭证、本地网络服务与固定时钟/屏障测试，不触真实凭证、真实用户配置或外网业务。
- 性能未测，不填虚构延迟/RSS 或零费用。M0 用固定策略后端原型，单并发、预热 5 次、100 次无交互启动、3 轮取 p95 中位轮，同时保存原始样本和峰值 RSS；pipes/PTY、补丁、图片分别测，排除人的答复时间。按实测基线留 2–3 倍余量冻结阈值，未冻结且未复测不能标待验收。授权与收尾次数/资源边界以实际运行结果为准。

## 2. 哪些情况容易出错

| 情况 | 期望结果 |
|---|---|
| 只声明模型能力，但未配置可信策略/没有专用宿主 | 不注册或执行本工具；旧模式不变；不能借聊天或伪造参数跳过启用条件 |
| 策略来自 .env、cwd、可写父目录；应用/bwrap 可替换、缺沙箱开关或后端不支持 | 明确拒绝启动 031 模式；不退回普通执行或 033 固定策略、不修改系统配置来掩盖失败 |
| 空权限、未知字段、旧数组、null、控制字符、超限输入 | 不显示允许界面，不扩大许可，按本工具错误结构回填 |
| 路径含 `..`、中文/空格/%XX、相似前缀、符号链接或不存在组件 | 逐组件验证并显示实际绝对路径；不越界、不解码、不自动改成更宽父目录 |
| 只批准 read，却尝试写/删/移动；批准父目录覆盖私有拒绝项 | 内核拒绝越权步骤；保留已知前序成功/部分状态语义，不能绕开永久拒绝 |
| 获批目录中预存敏感假文件的硬链接或 bind 别名 | 假文件正文仍不可得；M0 无法用实际后端证明时拒绝启用 031，不以遮蔽原路径代替验证 |
| 普通问询/聊天回答“允许”、旧窗口回执或终端控制注入 | 无授权；只有当前专用 typed 回执能提交；默认/关闭不等于允许 |
| 已覆盖申请重复、先允许后拒绝另一申请、同批后续执行 | 已覆盖不重问；拒绝新申请保留旧授权；同批后续仅在明确允许提交后使用新增范围 |
| 读写工具绕开 shell，或嵌套应用关闭自己的限制 | 补丁/模型看图也走受限入口；嵌套进程仍继承外层内核边界，不能返回主进程的挂载/进程视图或借其 fd 越权 |
| 新授权后继续输入旧 shell | 老进程权限不增加；另起进程才获得新快照 |
| 轮结束时额外权限命令还在运行，甚至 daemonize/setsid | 完整进程树终止；基线进程继续可续接；收尾失败不报告权限已撤销 |
| 申请后取消/断流/第 8 次请求上限；宿主崩溃 | 未提交不授予；所有退出路径执行额外进程收尾；已保存结果配对不丢，不自动重试 |
| 真实宿主和 user namespace 内 UID 不同；继承旧 /proc 或 fd | 以 host UID/实际命名空间核验；不靠 id 输出证明隔离；执行入口不满足则拒绝 |
| 保存并恢复原先 granted 结果或切换会话 | 只展示；旧授权/回答/句柄不能在新轮复活，失败的会话切换不混淆活动回执 |

## 3. 重要做法，为什么这样做

### 3.1 固定参考与本地取舍

- Codex 基线固定 `d138398cef7d49e46fe33f1d0ddbd2ca0ed16aa4`。[request_permissions.rs](https://github.com/openai/codex/blob/d138398cef7d49e46fe33f1d0ddbd2ca0ed16aa4/codex-rs/core/src/tools/handlers/request_permissions.rs)、[协议类型](https://github.com/openai/codex/blob/d138398cef7d49e46fe33f1d0ddbd2ca0ed16aa4/codex-rs/protocol/src/request_permissions.rs)及 [shell_spec.rs](https://github.com/openai/codex/blob/d138398cef7d49e46fe33f1d0ddbd2ca0ed16aa4/codex-rs/core/src/tools/handlers/shell_spec.rs)确认了“申请额外范围→等待宿主→实际授予权限→后续命令生效”的链路。首版只保留单环境与 turn 范围，用 status/error 明确本地拒绝和失败，不声称复制所有上游接口。
- 当前后端复用基线是 [033](033-tool-sandbox.md) 及其 `sandbox.rs`，上游来源固定为 `d8acdf151577132d4ee1de47a4d1822ae5acb762`。早期研究中的 [Linux helper README](https://github.com/openai/codex/blob/d138398cef7d49e46fe33f1d0ddbd2ca0ed16aa4/codex-rs/linux-sandbox/README.md)、[CLI](https://github.com/openai/codex/blob/d138398cef7d49e46fe33f1d0ddbd2ca0ed16aa4/codex-rs/linux-sandbox/src/linux_run_main.rs)和 [bwrap 构造](https://github.com/openai/codex/blob/d138398cef7d49e46fe33f1d0ddbd2ca0ed16aa4/codex-rs/linux-sandbox/src/bwrap.rs)保留为方案比较依据，不再要求另装一套独立 helper 或叠加旧降权链路。缺失能力复用来源与依赖由 M0 固定，不能省略本项目策略、别名边界与 PTY/进程树验证。
- [OpenAI Docs 的权限说明](https://learn.chatgpt.com/docs/agent-approvals-security)区分批准与 OS 沙箱；[权限后端文档](https://learn.chatgpt.com/docs/permissions)也说明平台无法执行的策略应拒绝。031 不把 027 的降权、F7 审计或 AGENTS.md 提醒替代成动态强制限制。
- [bubblewrap 项目说明](https://github.com/containers/bubblewrap)明确其调用方仍须正确构造策略；因此在统一入口补齐经过验证的策略与系统调用限制，不能把 033 的固定策略直接解释成动态授权。
- 只采用 turn 授权，避免在 007 会话中保存可恢复权限；对 016 的额外权限进程例外显式写入规格。基线权限和管理员上限由可信启动配置固定，不能由模型请求改变。
