# 规格：开发容器内安装 CC-Switch CLI

- 状态：已验收（2026-10-30 宿主重建镜像与容器后，运行验收通过；容器内证据见 `docs/logs/037-cc-switch-container/2026-10-30-runtime-acceptance.md`，宿主侧结论见 `docs/logs/037-cc-switch-container/2026-10-30-host-side-runtime.md`）
- 更新时间：2026-10-30

## 1. 要做什么，有哪些要求

重建开发容器后，dev 可直接使用最新稳定版 CC-Switch CLI，自己的设置和数据库可保留。

- R1. 构建时使用用户指定的官方 Release 安装脚本安装最新稳定版，程序进入镜像系统目录，不只存在于某个容器的可写层。
- R2. 普通 dev 用户在交互和非登录 shell 中均能直接运行 `cc-switch --version` 与 `cc-switch --help`，不需要 sudo 或手工补 PATH。
- R3. `/home/dev/.cc-switch` 绑定宿主项目的 `.container-state/cc-switch/`，保存数据库、设置、备份和技能文件。dev 可读写，停启或删除容器后使用同一持久目录，数据保留；已有旧数据先停止写入、备份迁移，不覆盖非空目标目录。
- R4. 只安装程序和准备自身数据目录，不在构建或验收时登录、切换供应商、同步真实 Agent 配置或启动代理服务，不把真实密钥写进镜像或仓库。
- R5. 安装全程非交互，下载或执行失败须让构建失败；主动更新重新执行安装层并记录实际版本，普通容器启动不联网升级。

用户指定的官方入口如下，配置在 Dockerfile 中，本轮不运行：

```bash
curl -fsSL https://github.com/SaladDay/cc-switch-cli/releases/latest/download/install.sh | bash
```

构建阶段允许设置官方安装目录参数与非交互覆盖参数，但仍使用该官方脚本。最新按主动刷新构建时的稳定 Release 判断，不写死调研时版本。不新增性能阈值，构建耗时和镜像增量与公共容器验证一起记录。

交付范围补充：按用户后续指令，本轮只准备配置和数据持久化，不构建镜像或重建容器。实施中原容器出现旧数据目录（含活跃数据库），已在写入进程停止后完成一致性校验迁移，并把当前容器切换到持久目录的符号链接（结果见 036 公共实施日志）；镜像安装与新容器运行验收仍待实际构建。

## 2. 哪些情况容易出错

- root 执行默认脚本 → 不应把唯一程序装到 `/root/.local/bin`，dev 必须能直接调用。
- 目标已有旧版 → 构建无人工确认，并按官方非交互参数完成目标程序替换。
- 脚本下载失败 → 不能因管道右侧空 Bash 成功而误报安装成功。
- 新卷首次挂载 → dev 可初始化自身数据库；遗留数据迁移后仍可写。
- 删除容器后重建 → 同一卷中的数据库能打开，假设置或标记保持；显式删卷不在保留承诺内。
- 验收继承现有 HOME 或 Agent 路径变量 → 必须重定向到临时目录，不读写真实凭证和配置。

## 3. 重要做法，为什么这样做

镜像系统路径保存 `cc-switch` 程序，宿主项目目录保存 `.cc-switch` 数据。安装阶段通过官方 `CC_SWITCH_INSTALL_DIR` 指定系统目录，通过 `CC_SWITCH_FORCE` 处理已有目标，最终保持 USER dev。

沿用官方 Linux 静态 musl 包的自动选择逻辑，不另写下载和架构识别器。共享 [Node/Pi 容器计划](../plans/2026-10-29-2202-feat-node-pi-container-plan.md)和验收入口，但本工具独立验收并单独记录证据。

依据见[调研汇总](../think-tank/2026-10-29-cc-switch-container.md)与[原始核实记录](../think-tank/raw/2026-10-29-cc-switch-container-official.md)。

## 4. 踩过的坑，怎样解决

官方 Release 下载链接在规划期的读取工具中未能直接取得正文；改为只读官方 v5.11.3 标签下的安装脚本及 README，并核对 Release 资产列表。实际构建时仍须核实 latest 安装结果，不能把静态检查当成安装成功。
