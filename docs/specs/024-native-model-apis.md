## 1. 要做什么，有哪些要求

### 1.1 范围

支持四类接口：**OpenAI Chat Completions、OpenAI Responses、Anthropic Messages、Google Gemini 原生接口**。“OpenAI Chat”在本项目里就是 Chat Completions，不新增另一种协议。

Gemini 的 Interactions 已正式发布，官方推荐新项目使用；`generateContent` 仍受支持。因此 Gemini 提供两个明确入口，共计五个 `protocol` 值：

| `protocol` | 官方基础地址示例 | 请求入口 | 鉴权 |
|---|---|---|---|
| `openai-chat` | `https://api.openai.com/v1` | `POST /chat/completions` | `Authorization: Bearer …` |
| `openai-responses` | `https://api.openai.com/v1` | `POST /responses` | `Authorization: Bearer …` |
| `anthropic-messages` | `https://api.anthropic.com/v1` | `POST /messages` | `x-api-key`，明确设置 `anthropic-version` |
| `google-interactions` | `https://generativelanguage.googleapis.com/v1` | `POST /interactions` | `x-goog-api-key` |
| `google-generate-content` | `https://generativelanguage.googleapis.com/v1beta` | `POST /models/{model}:generateContent` | `x-goog-api-key` |

Anthropic 初始版本固定为官方 SDK 当前声明的 `2026-10-21`；版本、请求样本和回放样本一起固定。Google Interactions 使用正式版 `v1`，不因正式版报错自动转入 `v1beta`。

“原生”指按该厂商协议直接发送和解析请求，不能统一转成 Chat Completions，再依赖服务端兼容层完成适配。同格式网关可以使用。首版使用 API Key；Bedrock、Vertex AI、OAuth、实时音视频、厂商托管搜索／代码执行、后台任务和服务端会话管理不在本次范围。

### 1.2 配置与模型目录

沿用 [002 配置与模型目录](002-llm-api-key.md)的厂商 ID、模型 ID、`base_url`、`protocol`、`key_ref`、`request_params` 和能力字段。旧配置不改也能使用，不改变现有默认模型。

- `protocol` 必须明确选择，不根据模型名、域名或错误响应猜测。未知值发送前报错；不自动切换协议、模型或凭证。
- 基础地址包含 API 版本，不包含具体操作路径；适配器只拼接一次，保留网关已有路径前缀。模型 ID 按所选协议的规则处理；中文、空格、`/`、`%` 不得因重复解码或编码而指向另一个模型。
- 继续只保存凭证引用；连接身份、换 Key 后缓存失效、刷新不影响已开始请求等规则沿用 002。一个用户轮固定其模型、连接和凭证。
- `request_params` 使用所选协议的原生字段。推理强度、thinking 配额、最大输出等不能不加区分地复制到其他协议。已确认不支持的参数明确报错；能力未知时不自动添加可选参数，沿用 002 的显式能力声明规则。
- 模型、消息、系统指令、工具、工具结果和续接状态由宿主维护，扩展参数不能覆盖。Responses／Interactions 的 `store` 和 `previous_*` 也属于宿主管理字段。报错应指出冲突字段。
- Messages 必需的输出上限取显式配置的 `max_tokens`，或目录里已知的 `max_output`；两者都没有时，发送前提示补配置，不猜一个数。
- `/refresh` 使用对应厂商的原生模型列表及鉴权，按官方游标读完分页；入口不支持列举时，仍允许手动配置模型。Google 的资源名与执行模型 ID 采用明确、可往返的转换。不得因为“查到了模型”就推断它支持图片、工具或某个参数。
- 目录的完整替换、合法空名单、最多 100 页、失败保留同身份旧数据、身份变化排除旧数据等规则继续遵守 002，不写半份名单。

### 1.3 一次调用的输入与输出

输入是已固定的模型连接、系统指令、有序历史、工具定义和本协议参数。输出统一表达可见文本、有序工具调用、必要的原生续接内容、结束原因、厂商提供的用量或明确错误。

普通 CLI、TUI、记忆提取和记忆合并都必须通过同一接口边界。不能主界面支持了原生协议，内部记忆请求仍偷偷走 `/chat/completions` 或只解析 `choices[0].message`。

必备能力：多轮文字、现有用户图片和 `view_image` 返回图片、普通函数工具、工具结果回传，以及记忆功能已使用的结构化输出。按模型已知能力决定是否开放；不支持或缺少必要声明时，在发送／执行前说明原因，不丢图、不静默降级。图片准备、大小和本地读取边界沿用 [019](019-view-image.md)、[020](020-cli-image-input.md)。

同时支持完整 JSON 响应和原生 SSE 响应。默认保持现有非流式行为；显式启用 `stream` 时按所选协议请求 SSE，`generateContent` 改用 `:streamGenerateContent?alt=sse`。本次只要求正确组装完整回答，不新增逐 token 渲染功能。SSE 必须收到合法完成事件才提交回答或执行工具。

### 1.4 工具循环与原生状态

| 接口 | 必须正确处理的内容 |
|---|---|
| Chat Completions | `messages`、`tools[].function`、`tool_calls` 和 `tool_call_id`，保持现有行为 |
| Responses | 有序输入／输出 Items、`function_call`、`function_call_output`；用 `call_id` 配对，不能拿 Item 的 `id` 替代；保留续接所需的 reasoning 等 Items |
| Messages | 有序 content blocks、`tool_use`、`tool_result`；按 `tool_use.id`／`tool_use_id` 配对，结果放在协议要求的 user 内容中；保留 thinking／签名块 |
| Gemini Interactions | 按顺序处理 `steps`，保留 thought 等续接步骤；`function_result.call_id` 对应 `function_call.id` |
| Gemini generateContent | `contents/parts`、`functionCall`／`functionResponse`，保留原有 Parts、顺序及 `thoughtSignature` |

- 宿主仍共用一套工具目录、权限、路由和执行逻辑，不为每个接口复制执行器。MCP 的服务器身份、每轮快照和凭证污染拒绝继续遵守 [022](022-mcp-tools.md)。
- 模型返回字符串形式的 `id`、`name`、`arguments` 时，沿用 [006](006-tool-call-loop.md)原样保留；执行路由不做 trim、改名或容错匹配。原生对象参数只做必需的 JSON 转换，不虚构“原始参数字符串”。
- 旧 Gemini 响应可能没有调用 ID：只允许宿主生成稳定的内部配对 ID，并保存其映射；不得把它冒充厂商返回的 ID。原生回传遵守该协议实际支持的字段。
- 整个响应及同批调用先做协议结构校验，再执行。参数碎片未收齐、流中断、必需字段缺失／类型错误、重复／错配 ID、超限调用批次或不支持的动作类型，均不能触发这一批的部分执行。
- 非空但未知的函数名、字符串参数里的非法 JSON、工具 Schema／业务参数错误属于单个工具失败，按 006 回传对应失败结果；同批其他合法工具照常执行，模型可以继续纠正。不能把这些错误升级成整批协议错误。
- HTTP、响应结构解析或续接状态错误结束本轮。任何适配器或 SDK 都不能自动重发已发送的模型请求，也不能重放工具。
- 用户轮继续保持最多 8 次模型请求、每批最多 32 个工具调用、按返回顺序串行执行；第 8 次返回的合法工具批次仍完成并保存，再停止。SSE 事件不另算模型请求。记忆合并仍使用它自己的工具白名单与既有限额。
- Responses 和 Interactions 使用客户端完整历史与 `store:false`，不依赖 `previous_response_id`／`previous_interaction_id`；不承诺此设置改变厂商的其他数据保留政策。
- 必要的原生内容与对应 assistant 记录一起保存：opaque 字符串逐字保留、块顺序不变、不删改未知但续接必需的字段。不解密、不伪造签名，也不当作可见正文、系统指令或记忆摘要。
- 原生状态绑定厂商配置、协议、模型和 002 定义的连接身份。不能发送到其他来源。切换来源只允许在轮与轮之间：已闭合的旧对话保留可见内容与工具结果；对目标协议无法合法表达的旧工具块，转成明确标注的历史文本，不伪造该目标模型的签名或调用。未闭合的原生调用链不能跨来源续接，应明确报错。

### 1.5 保存与恢复

[007 会话格式](007-session-persistence.md)的 V1 无法完整表达上述原生块。本功能引入 V2，具体约束如下：

1. 新程序读取 V1 和 V2；只用既有 Chat Completions 内容时继续写 V1。V2 保存共同历史及原生块、所属身份、配对映射，不能只保存界面文字。
2. 首次产生需要 V2 的内容时，创建新的 V2 自动会话文件，以完整上下文开篇，再继续追加；不原地改写或混写旧 V1 文件。包含原生状态的 `/save` 快照写 V2。
3. 记录本体和它的原生状态同一条提交，避免只保存一半。沿用 007 的锁、坏行处理、64 MiB 行上限、权限和保存失败语义，不增加 fsync／掉电保证。
4. 旧程序遇到 V2 必须明确拒绝，不能忽略原生字段后声称无损恢复。新程序遇到损坏的必要状态，允许显示可恢复历史，但必须阻止需要该状态的续接；不能编造状态或重新执行工具补齐。
5. `/resume` 只恢复历史，不发请求、不重新执行工具、不恢复旧进程控制句柄。相同来源恢复后的下一请求，原生必需内容与保存前一致。

会话仍可能含用户及工具提供的秘密，沿用 007 的私有文件保护，不新增“自动清除全部秘密”的承诺。宿主不得主动写入鉴权凭证；原生状态不是凭证存储容器。

### 1.6 错误和资源边界

- 本地输入／能力／保留字段错误：零 HTTP 请求、零工具副作用。HTTP 400／401／403／404／429／5xx、网络错误、超时、非预期 Content-Type、坏 JSON／SSE 和输出不完整：明确失败，不换协议、不自动重试。
- 错误包含厂商、模型、协议和可用的 HTTP 状态／请求 ID，使用现有凭证保护后再显示；不输出鉴权头、Key、指纹或完整原始请求。厂商错误正文也按不可信内容处理。
- 延用当前连接超时 10 秒、请求总时限 180 秒、禁止自动重定向。分块到达不重置总时限；取消后不执行未提交的工具。
- 序列化后的出站请求与累计入站响应分别最多 10 MiB；恰好上限允许，超过就拒绝。SSE 原始累计字节及组装结果都受界限约束，不能靠增量读取绕过。图片内联、签名和工具 Schema 都算入请求体。
- 厂商用量字段按实际可得信息保存，缺失记为未知，不写 0；输入、输出、缓存和推理用量不能无依据地相加。真实 API 费用、存储和带宽费用本次均为未测。

### 1.7 速度与资源的测法

2026-10-25 已测首次实现原型基线，并按各组实测值的 **3 倍冻结延迟与内存上限**。这是核心接口接通后的首次测量，没有更早原型的数据，不倒填。调度、终端 I/O 和本地服务会有波动，留 3 倍余量；后续审查／修复不得为了过关放宽阈值。

| 协议 | 六组负载中最差 p95 | 最高峰值 RSS |
|---|---:|---:|
| Chat Completions | 11.435 ms | 23,048 KiB |
| Responses | 10.465 ms | 23,316 KiB |
| Messages | 12.871 ms | 23,256 KiB |
| Interactions | 13.431 ms | 23,408 KiB |
| generateContent | 12.872 ms | 23,432 KiB |

各组精确阈值、18,000 个正式样本和机器／锁文件信息见[基线 JSON](../logs/024-native-model-apis/performance-baseline.json)；[源文件归档](../logs/024-native-model-apis/performance-baseline.source.tar.gz)与本记录的起点提交共同固定原型。不能拿上表的汇总最大值替代某一组较小的阈值。最终实现还须使用同一脚本和固定阈值复测。

固定本地独立 mock 进程、并发 1、预热 20 次、正式 200 次、3 轮，延迟取三轮中最大的 p95；分别测纯文字、32 调用批次、带准备后图片的请求、JSON 和 SSE。先用同一客户端对最小回显服务跑相同负载，确认客户端开销；不拿公网模型耗时衡量适配器速度。

记录 CPU／内存、OS、Rust、依赖锁文件、构建模式、载荷字节数和样本原始数据；内存测目标 CLI 进程预热后至本轮结束的峰值，并记录与纯 Chat Completions 基线的差。本轮差值为 −184 至 +540 KiB，包含进程波动。控制组使用同一 CLI／ureq 客户端的最小固定 Chat Completions 回应，结果包含 CLI 开销，不是纯网络延迟。更换机器、客户端或实现语言后重测，不直接比较旧数字。费用按“实付／估算／未测”记录，离线测试不能写成真实调用费用为 0。

## 2. 哪些情况容易出错

| 情况 | 期望结果 |
|---|---|
| 把同一模型地址换成另一个协议；远端返回 404 | 只用配置的协议，清楚报错，不偷偷尝试其他路径 |
| 轮内刷新配置、同名引用换 Key，或另起一个会话 | 当前轮身份固定；新轮用新身份；目录与原生状态不串用 |
| 同一批工具出现重复 ID，或后项缺必需协议字段 | 整批先拒绝，不能先执行前几个；原有名称与 ID 不被修正 |
| 同一批有未知函数名、非法 JSON 参数和合法调用 | 错误项各回失败结果，合法项照常执行；循环继续，名称不被修正 |
| SSE 参数按字符分段、多调用交错、中途断开或完成事件缺失 | 正确组装和关联；不完整时这一批零工具执行 |
| thinking／签名块夹在文字与工具之间 | 原样、按原顺序续接，不只提取最终文字 |
| 第 8 次模型请求还返回工具；返回 32／33 个调用 | 第 8 次合法批次照常完成后停止；32 可执行、33 整批拒绝 |
| 原生工具结果包含图片或错误文本 | 在该协议合法位置回传；不能丢图，也不把错误当成成功 |
| 切换厂商、协议、模型、地址或 Key 后继续 | 不跨来源回传原生状态，不重跑历史工具；未闭合链明确拒绝 |
| V1 恢复后首次产生原生状态、V2 半行损坏或被旧程序读取 | 新建 V2 保留上下文；必要状态缺失就阻止续接；旧程序拒绝 V2 |
| 两个进程恢复同一自动会话 | 沿用独占锁与只读降级，不互相覆盖，不复制执行工具 |
| 模型列表重复游标、中途鉴权失败、合法空名单 | 前两者不替换旧名单；空名单正常替换；不跨身份借缓存 |
| 模型 ID 含 Unicode、空格、斜杠、百分号或已有转义 | 按协议明确转换并断言实际路径和模型字段，不重复解码／编码 |
| 总体积恰好 10 MiB／多 1 字节；流不断到达但超过 180 秒 | 边界允许、超限拒绝；总时限不因持续分块而延长 |
| 只有 ID、能力未知；参数／图片能力已确认不支持 | 基础文字可用；不猜能力；可选功能按 002／019／020 检查 |
| 错误正文含 Key、重定向到另一个域名 | 按现有凭证保护显示错误，不跟随重定向，不转发凭证 |

## 3. 重要做法，为什么这样做

### 3.1 共用业务，分别处理协议

保留项目现有 Rust 工具执行与会话管理。共同层负责对话顺序、工具权限和执行结果；适配器只负责路径、鉴权、参数与消息转换、原生状态、响应／SSE 和错误解析。共同历史不能定义成“Chat Completions JSON”，否则其他协议的状态会在转换时丢失。

实现前逐一核对普通 CLI、TUI、记忆提取和记忆合并的调用点。原生状态需要独立保留，但不建立第二套可变历史；界面展示仍来自共同记录。

### 3.2 复用经过核实的代码

Responses 参考固定提交的 Codex 客户端及 Item／流处理方式，按本项目的手动会话、普通函数工具和错误边界裁剪，不整套引入 Codex core。

Anthropic、Gemini 优先检查 Rig 等成熟 Rust 客户端的协议转换，官方 SDK 用作字段和行为依据。先用最小探针证明：能保留原生状态、关闭自动重试、限制响应体、按需取消，并覆盖本规格选定的 API 版本。通过才复用；不能满足时，复用可确认的转换部分，补最小适配。候选和固定源码见调研记录，不将“仓库里有这个 provider”当作已满足要求。

### 3.3 后续工具能力使用这层接口

本功能只提供各协议的普通函数声明、调用和结果能力。后续 MCP 资源及工具搜索共用宿主工具目录，再分别生成原生定义。Responses／Anthropic／Gemini 的服务端工具搜索不是同一种功能，不能只改工具名就当作已支持；由后续工具规格决定使用原生机制还是本地普通函数适配。

### 3.4 落地顺序

1. 固化共同记录、V1／V2 和五个协议的请求／响应夹具，测最小原型基线 → 检查旧配置及会话不变，补齐并冻结性能数字。
2. 保留 `openai-chat`，接入 Responses，再接入 Messages 与 Gemini 两个入口 → 逐个验证文字、工具多轮、原生状态、JSON／SSE、图片与错误。
3. 接通模型目录、记忆调用、CLI／TUI、保存与恢复 → 检查没有遗留的 Chat Completions 专用调用路径。
4. 按第 5 节完成规定验证，交由独立验收 → 本规格通过后，再继续工具实现计划。

各步均按项目规定先写能失败的行为测试，再实现；不顺带重写 TUI、记忆系统或 MCP 传输。

## 4. 踩过的坑，怎样解决

已发现并处理编译环境无法创建线程、公共入口校验缺口等问题；记忆 V2 读取缺口正在补验证。实际失败、根因及复验结果统一见[实施记录](../logs/024-native-model-apis/2026-10-24-implementation.md)，不把第 2 节预警当作实测故障。

2026-10-25 收口新增四坑：外部 SSE 的 `interaction` 字段未验型即在组装时索引赋值会 panic（先验对象再保存）；Gemini `functionCall.args` 官方可省略，强制对象会误拒合法无参调用（缺省与 null 按 `{}`，显式非对象仍拒）；`stream` 曾绕过统一能力门（与其它可选参数同走 `check_request_param`）；旧历史非法 JSON 参数对对象参数协议曾整轮阻断（转明确标注历史文本，同批混合时整块保守转换）。红绿证据见实施记录“交付收口”一节。

本轮已经确认的接口路线与“原生状态不能压成纯文字”的决策见 [project-lessons.md](../../rules/project-lessons.md)。资料核对与运行结果分开记录，不能用查过官方文档代替接通验证。

### 5.2 验证方式与证据

- 先确认相关测试原有状态，再按 **TDD → comprehensive-testing → Security Testing → code-review → 全量验证和修复** 执行；发现错误使用 `diagnosing-bugs` 定位。关键用例用修复前后对照或临时破坏行为证明能检出错误，断言保持不变。
- HTTP／SSE 使用固定边界服务驱动真实适配器，不能 Mock 掉本次协议转换；E2E 启动真实 CLI／PTY，检查用户看到的结果，并用请求记录、退出码及临时文件证明动作执行。模拟时钟与固定载荷验证超时、身份变化和边界。
- 仓库 `/workspace` 的最终统一命令：`cargo check && cargo test --workspace --no-fail-fast`，包括 CLI／TUI 的 E2E；单独排查 E2E 可用 `cargo test --test e2e_acceptance`。新增用例必须由全量命令自动覆盖，不能只交定向结果。副本运行使用专用 `--target-dir`。
- typecheck／lint 按实施时核实的工具链运行，如不可用如实记录；新程序读 V1／V2、旧程序拒绝 V2 用固定夹具和隔离旧版产物验证，不新增不适用的通用兼容检查工具。
- 证据放 `docs/logs/024-native-model-apis/`，记录基线、环境、命令、固定样本、请求摘要、关键输出、失败原因、反证、通过／失败／跳过／未运行数量。沿用本次调研记录作为入口，不复制出相互冲突的结论。
