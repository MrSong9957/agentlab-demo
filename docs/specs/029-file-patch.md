## 1. 要做什么，有哪些要求

### 1.1 目标与范围

补齐原对照表「文件补丁」一行内的两处剩余差异，作为同一项任务交付：

- 移动与重命名：通过现有 `apply_patch` 把 UTF-8 常规文本文件移动到新路径，并可在同一块中修改内容，复用 Codex 的 `*** Move to: ...` 语法。
- Unicode 标点与空格匹配容差：在现有三级匹配均失败后，按固定上游映射再次定位补丁上下文；普通 Update 和带 Move 的 Update 使用同一规则。

保留 JSON 参数封装、禁止覆盖目标、四字段结果、已有 Add/Update/Delete 行为及资源边界。二进制、目录移动、覆盖目标、自由文本工具接口和多文件事务不在范围内。

任务粒度按用户指定的原表行确定；这两个差异属于「文件补丁」的内部要求，不拆成下一项任务。其余原表行各用独立规格与实施计划；六项规划现已建立，开始哪一项实施仍由用户决定。

### 1.2 移动与重命名：输入与路径

- 工具名和参数不变：`apply_patch`，唯一必填字符串 `patch`，未知 JSON 字段继续拒绝。
- `*** Move to: 目标路径` 只允许紧接 `*** Update File: 源路径`，同一 Update 块最多一次；后面可以没有修改块（纯移动），也可以接已有 `@@` 修改块。
- 仅含源路径而没有 Move 或变更的空 Update 仍属非法；空 `@@` 仍属非法。重复、位置错误或空目标的 Move 标记必须在完整解析阶段拒绝，整个补丁不发生文件操作。带上下文前缀的 ` *** Move to: ...` 仍是文件内容，不当成指令。
- 源和目标各自按会话当前工作目录解析；绝对路径原样使用。沿用现有路径拼写与空白处理，不新增 URL 解码、变量或 `~` 展开，不用 canonicalize 改写结果路径；支持中文和路径中间的空格。未启用 033 沙箱（普通模式）时**没有路径边界**——`../`、绝对路径与目录符号链接均属执行环境信任面，路径强制的唯一边界是 `TCHAT_SANDBOX` 沙箱模式（2026-10-28 攻防实测确认，见[安全报告](../security/reports/2026-10-28-029-apply-patch-move-security.md)）。
- 源必须存在、是有效 UTF-8 常规文件；本次新增的 Move 分支拒绝源路径末端的符号链接（包括悬空链接），避免复制链接所指内容后删除链接本体。普通 Update 原有的链接语义不变。
- 目标不得已经存在，包括常规文件、目录、符号链接、悬空链接和指向源的硬链接。源、目标指向同一路径时也拒绝，不退化成普通 Update。目标父目录缺失时沿用 Add 的创建策略；权限由当前执行身份及执行环境控制。

纯移动示例：

```text
*** Begin Patch
*** Update File: notes/旧名.txt
*** Move to: archive/新名.txt
*** End Patch
```

移动并修改示例：

```text
*** Begin Patch
*** Update File: src/old.txt
*** Move to: src/new.txt
@@
-mode=dev
+mode=test
*** End Patch
```

### 1.3 Unicode 匹配容差

在 `seek_sequence` 中按以下顺序搜索：精确匹配 → 忽略行尾空白 → 忽略两端空白 → 忽略两端空白并应用下表字符映射。每一级都先扫描完整的允许范围，全部失败后才尝试下一级；不能逐候选位置直接尝试所有级别，导致前面的宽松匹配抢走后面的精确匹配。

| 源文与补丁两侧分别用于比较的字符 | 比较时映射为 |
|---|---|
| U+2010–U+2015、U+2212 | ASCII 连字符 `-` |
| U+2018–U+201B | ASCII 单引号 `'` |
| U+201C–U+201F | ASCII 双引号 `"` |
| U+00A0、U+2002–U+200A、U+202F、U+205F、U+3000 | ASCII 空格 U+0020 |

- 固定采用上表 28 个码点的映射，比较前对每行调用既有 `trim` 规则；两侧都映射，因此 Unicode 字符与 ASCII 字符之间、同一映射组内部均可匹配。中文、大小写和未列出的行内字符保持区分，不做 NFC/NFKC、大小写折叠或连续空格合并。
- 既有 `start` 搜索起点、同一级取最早候选、模式长于文件拒绝、空模式和 EOF 锚定规则不变；`@@ 定位上下文` 与变更块中的旧行均通过同一搜索逻辑。
- 映射只用于定位，不改写源文件缓冲、文件路径或补丁中的新增文本。未修改的上下文行保留源文真实 Unicode 字符和原行尾；新增/替换内容按补丁原样写入，行尾遵循 004。结果与 TUI 差异仍来自真实前后内容。
- 四级均不匹配时按现有上下文失败处理，在当前文件写入前停止；带 Move 的块也不得先创建目标或删除源。不增加开关、协议参数或新依赖。

### 1.4 移动的文件行为与失败语义

1. 继续先完整解析整个补丁，再按块顺序执行；每块执行时读取当时的文件状态。后续块可以使用前序移动后的目标；一个块失败即停止，不回滚前序成功操作。
2. 对 Move 块先完成源文件判型、有界读取、UTF-8 与内容校验，再计算目标内容。纯移动逐字节保留源内容，包括混合行尾和缺失的末尾换行；有修改块时按 §1.3 的四级规则匹配，行尾沿用 004。
3. 采用「创建目标并完整写入，再删除源」的顺序。目标必须以排他创建保证不覆盖；仅做存在性预检不合格。目标写入未完成前，不得删除或改写源内容。
4. 完整写入目标后，立即把目标的成功创建加入变更清单；源删除成功后再加入源删除。删除失败时保留已经写好的目标，不自动清理或重试；用户和模型依据结果重读后决定下一步。
5. 写目标或删源等变更步骤失败，沿用保守语义 `state_known=false`。若目标可能被部分写入，不把它列为已完成的 `add`；若目标已经完整写入而删源失败，清单必须包含目标 `add`。错误含源、目标的可确定绝对路径和失败阶段。
6. 读入时的源对象必须经已打开 fd 判型；Move 分支不得通过跟随源末端链接绕过拒绝规则。删除前复核源路径仍对应读入对象；检测到源对象更换时停止，保留已知成功清单并提示重读。工具仍按既有串行顺序执行；不新增跨进程锁，也不承诺与外部并发改写之间的事务隔离。
7. 这是文本内容的「新建＋删除」，不承诺 inode、权限位、所有者、时间戳或扩展属性随源保留；目标文件权限沿用现有 Add 创建策略。进程崩溃或断电时不承诺原子移动、持久化事务或自动恢复。

### 1.5 结果、展示与兼容

- 结果继续固定四字段 `ok / changed_files / state_known / error`，动作仍只有 `add / update / delete`，不新增 `move` 枚举或结果字段。
- 一个成功 Move 返回两条记录，顺序是目标 `add`、源 `delete`。同一补丁内不去重，按实际完成顺序记录。完全成功为 `ok=true`、`state_known=true`、`error=null`。
- CLI 的工具结果保留两条记录；TUI 复用现有 Add 与 Delete 展示，分别用目标真实新内容和源真实旧内容生成卡片。部分成功时只展示已经确认完成的文件操作，并显示失败及未知状态；不能把计划中的源删除画成成功。
- 会话保存仍使用既有工具结果和 `PatchChangeKind::Add/Delete`。恢复后展示与执行时一致，只展示历史，不重做移动。旧会话继续加载；不升级会话格式，不添加专门的重命名组件。
- 普通执行与 033 沙箱执行复用同一套核心逻辑。沙箱路径为 `apply_patch_sandboxed → tool_launch_argv → --internal-apply`，读取源、创建目标、删除源均在沙箱子进程内完成，主进程不得代读、代写或代删。033 已替代旧双账号链路，不再以 UID 不同作为生效证据；策略锚定主进程工作区，不随模型指定的 workdir 改变，包装失败必须明确失败。

假设会话目录为 `/work`，移动并修改成功的模型结果为：

```json
{
  "ok": true,
  "changed_files": [
    {"path": "/work/src/new.txt", "action": "add"},
    {"path": "/work/src/old.txt", "action": "delete"}
  ],
  "state_known": true,
  "error": null
}
```

### 1.6 测试条件与资源边界

- 使用仓库当前 Linux 容器和 Cargo.lock 锁定依赖；实施时记录实际 OS、CPU、Rust/Cargo 版本与执行身份，不照抄历史环境数据。
- 测试只使用独立临时目录和假数据；涉及配置、HOME、缓存及会话时重定向到临时目录。路径竞争用屏障协调，写入故障用独立子进程的固定资源限制；不靠随机、真实当前时间或碰运气的等待复现。
- 原有上限继续适用：补丁最多 1 MiB；源读入与目标生成内容分别最多 4 MiB、100000 逻辑行。读入须有限，生成结果须在创建目标或修改目录前检查；超限不得写入目标或删除源。
- 不增加网络或模型请求，不引入额外依赖；本项不设没有基线依据的延迟阈值。资源验收以现有字节数和行数上限及顺序逐文件处理为准；运行耗时、峰值内存与费用当前均未测，不记作 0。

## 2. 哪些情况容易出错

| 情况 | 期望结果 |
|---|---|
| Move 出现在 Add/Delete、重复或位于修改行之后；空目标 | 完整解析失败；包括合法前序块在内均不执行；`ok=false`、空清单、`state_known=true` |
| 源缺失、是链接或非常规文件、不是 UTF-8；内容不匹配或超限 | 当前块不创建目标、不删源；保留前序成功清单；`state_known=true` |
| 目标已存在，或预检后被另一个进程抢先创建 | 不覆盖目标、不删源；只有创建竞争且未产生本次变更时，仍为已知状态 |
| 源、目标同名，或通过 `.`、`..`、已有别名指向同一文件 | 按目标冲突拒绝，不删除源；不得靠字符串不同绕过禁止覆盖 |
| 目标父目录不存在或没有写权限 | 允许按 Add 创建缺失父目录；权限失败停止；已经尝试变更目录或文件的失败保守标记状态未知，不删源 |
| 写目标中途失败 | 源内容完整保留；目标可能残留部分内容；目标不列为完整 `add`，`state_known=false`，要求重读 |
| 目标写好，删源失败或检测到源对象更换 | 清单保留目标 `add`，不记源 `delete`；`ok=false`、`state_known=false`；可检测的替换对象不得被删 |
| 同一补丁 A→B，再 B→C；多个块使用同一路径 | 按块读取最新状态；成功清单依次追加，不去重；后块失败不回滚前块 |
| 重复提交同一成功移动补丁 | 第二次因源缺失或目标冲突失败，不新增成功记录，不改动第一次的目标内容 |
| 中文、空格、CRLF、混合行尾、空文件、无末尾换行 | 路径解析正确；纯移动字节不变；移动并修改及普通 Update 遵守 §1.3 匹配和 004 行尾规则 |
| 后面的精确/空白容差匹配与前面的 Unicode 容差匹配同时可用 | 先完成整段较严格级别的搜索，选择较严格匹配；仅同级候选按位置取最早 |
| `@@` 或旧行只在上表字符上有差别；连续多块带 start/EOF 限制 | 第四级可定位，但不得越过起点或改变 EOF 规则；普通 Update 与 Move 块结果一致 |
| 匹配成功但源上下文有弯引号、特殊空格及混合行尾 | 原有上下文字节保留，新增文字保留补丁原字符；不能把比较映射写回文件 |
| 行内全角字母、组合字符、大小写或未映射标点不同 | 保持不匹配，当前块不写文件；不把 Unicode 容差扩大成任意相似文本匹配 |
| 重启并 `/resume` | 展示已记录的两项成功或部分成功；文件不再被移动；旧记录不迁移、不报错 |
| 开启 033 沙箱，读取被遮蔽的 .env，或向工作区及系统临时目录以外的只读位置移动 | 敏感正文不可得、越界写入被拒绝；主进程不能代办；允许范围内的正例成功，实际状态与部分成功结果一致 |

## 3. 重要做法，为什么这样做

### 3.1 复用依据与取舍

- 上游固定在 `openai/codex@d138398cef7d49e46fe33f1d0ddbd2ca0ed16aa4`。复用 [Update 的可选 move_path 与语法](https://github.com/openai/codex/blob/d138398cef7d49e46fe33f1d0ddbd2ca0ed16aa4/codex-rs/apply-patch/src/parser.rs)及[先写目标后删源的顺序](https://github.com/openai/codex/blob/d138398cef7d49e46fe33f1d0ddbd2ca0ed16aa4/codex-rs/apply-patch/src/lib.rs#L550)。[OpenAI Docs 的补丁语法](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide)也把 Move 列为 Update 的可选部分；这不要求更换本项目的 JSON 参数封装。
- Unicode 第四级映射复用同一固定提交的 [seek_sequence.rs](https://github.com/openai/codex/blob/d138398cef7d49e46fe33f1d0ddbd2ca0ed16aa4/codex-rs/apply-patch/src/seek_sequence.rs)；已有三级匹配优先级保留，只为前三次失败添加最后一轮比较，不改写原文。
- 继续使用现有本地实现，只移植所需语法与匹配逻辑；保留本地禁止覆盖、资源上限和四字段结果，不照搬上游覆盖目标的行为。
- 用现有 Add/Delete 表达两个实际文件操作，能复用工具结果、展示与会话格式；代价是界面显示为新增和删除，且不保留源元数据。该取舍是本规格的一部分。
- 当前执行器一个块只返回一条成功变更，直接添加 Move 会漏掉块内部分成功。实施时按已完成的文件操作及时累积结果与展示，不等整个 Move 成功后才补清单。

### 3.2 根据规格制定的实施计划

以下步骤均属于原表「文件补丁」同一项任务。M1–M5 按依赖顺序逐步 TDD；M6 的门禁按仓库规定顺序执行。本轮只制定计划，不执行实现。

| 步骤 | 修改落点与工作 | 验证与退出条件 |
|---|---|---|
| M0 固定基线 | 记录现有工作区改动和相关测试原有结果；冻结移动与 Unicode 匹配两部分的输入、优先级、结果和失败语义，核对 033 统一入口、部署记录及固定策略 | 已有失败与新增失败可区分；普通模式与真实 bwrap 分支分别有基线；规格争议先交用户裁决，不自行改验收要求 |
| M1 语法 | `src/app/src/apply_patch.rs` 的 `Hunk::Update`、完整解析与空块检查增加可选移动目标；先补纯移动、移动并修改、重复/错位/空 Move 测试 | 新正例在旧实现失败，支持后通过；非法语法始终不触文件；旧的空 Update/空 @@ 规则保留 |
| M2 文件操作与部分成功 | 同文件中的 `run/apply_hunk` 接通有界源读取、内容计算、排他创建目标、完整写入、复核并删除源；复用现有 fd 判型与 Add 创建策略；按实际完成步骤累积多条变更及展示 | 真实文件系统核对成功、目标竞争、半写、删源失败和源替换；每条记录均对应实际完成操作；源在写目标失败时完整保留 |
