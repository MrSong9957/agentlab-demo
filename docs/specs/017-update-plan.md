## 1. 目标与范围

只补齐一条链路：**模型调用 `update_plan` → 校验参数 → 用户看到计划清单 → 更新步骤状态 → 保存后可恢复显示**。

本次只新增 `update_plan` 一个工具。参数、状态、解析规则和清单显示优先复用 Codex，只适配本项目已有的工具循环、终端和会话历史。

计划只是步骤和进度的记录。模型决定做什么、何时更新状态，实际工作仍由已有工具执行；宿主不根据步骤文字执行命令，也不根据测试结果自动修改计划。

范围只含任务计划，不引入 Plan Mode、其他新工具、调度器、固定侧栏、独立计划数据库或新的 API 协议。每轮 8 次模型请求、单批 32 条工具调用及现有取消语义保持。

## 3. 计划接口与行为

### 3.1 输入：沿用 Codex

```json
{
  "explanation": "实现完成，开始验证",
  "plan": [
    {"step": "接入计划工具", "status": "completed"},
    {"step": "验证计划显示与恢复", "status": "in_progress"}
  ]
}
```

- `plan` 必填，每项必须有字符串 `step` 和枚举 `status`；状态仅为 `pending / in_progress / completed`。
- `explanation` 可省略；按上游 Serde 语义，省略或 `null` 均表示无说明。
- 顶层和步骤项均拒绝未知字段；非法 JSON、缺字段、错误类型和非法状态返回参数错误。
- 保留上游实际接受的输入：空数组、空步骤字符串、多个 `in_progress` 不额外拒绝。工具描述和提示词仍要求至多一个进行中，但不新增上游没有的运行时计数校验。
- 每次传入完整计划，步骤顺序与原文保留；没有步骤 ID、局部更新或额外状态，也不自动修正模型输入。

### 3.2 结果与调用循环

本地工具结果固定为两个字段：

```json
{"ok": true, "error": null}
```

失败时为 `{"ok":false,"error":"具体原因"}`。成功含义等同 Codex 的 `Plan updated`，只确认本次更新被接受，不保证实际工作已经完成。结果不重复返回整份计划。

- 普通用户轮和带记忆摘要的用户轮均开放该工具，工具数由三项增至四项；内部记忆合并轮保持原受限工具面，分派层拒绝 `update_plan`。
- 复用现有调用 ID、名称原样保留、结果配对、串行执行和错误回传规则。参数错误作为工具结果回传，不升级为协议错误或自动重试。
- 取消前已接受的更新保留；取消后跳过的调用返回相同两字段失败结构，错误沿用 `SKIPPED_BY_CANCEL_MESSAGE`，不产生成功计划快照。
- 沿用现有 `TurnNotify::ToolEnd`，不新增专用事件总线、计划管理器或后台任务。
- 每轮仍最多 8 次模型请求，按请求计数而非按步骤或单次响应里的工具数量计数。第 8 次返回合法调用时，执行并保存结果后按现有规则报上限，不发第 9 次请求。
- 取消、请求失败或额度耗尽均不自动把未完成步骤改成完成。下一用户轮可继续提交完整计划。

### 3.3 显示与会话恢复

- **TUI**：成功更新追加一条完整计划快照，复用 Codex 的状态标记、说明和清单渲染；旧快照作为历史保留。空数组显示上游的无步骤提示。失败与取消显示原因，不把失败调用的参数画成成功清单。
- **普通命令行**：保留工具活动行，在成功结束通知中输出说明与步骤，并用“待办／进行中／已完成”标明状态；不依赖颜色区分。空数组明确显示“暂无步骤”。失败与取消输出原因。
- **显示安全**：步骤和说明在进入终端展示前复用 `display::sanitize_for_terminal`；只过滤展示副本，原始调用参数仍按现有历史契约保存。
- **保存**：继续使用 V1 的 `AssistantToolCalls` 和配对 `ToolResult`，`display` 保持 `None`；不新增持久化枚举变体、文件或数据库。
- **恢复**：只有配对结果明确为 `ok=true`、`error=null`，且参数可按同一规则解析时，才重建成功快照。失败、取消、结果未知、参数损坏或未配对的记录沿用错误／普通文本降级，不推断已经成功。
- **投影一致**：实时和恢复共用计划结果转换及同一 TUI cell。恢复只展示，不重新调用工具；没有单独保存的“当前计划”，最近一次成功快照就是最近的更新。
