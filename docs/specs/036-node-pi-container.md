# 规格：开发容器内安装 Node.js 与最新 Pi Agent

- 状态：待验收（本轮授权的配置与数据迁移已完成；镜像构建后的运行验收待实际构建时执行）
- 更新时间：2026-10-29

## 1. 要做什么，有哪些要求

让开发者重建容器后即可使用 Node.js、npm 和最新稳定版 Pi Coding Agent，并继续使用已有的 Pi 配置与会话。

- R1. 镜像构建时安装官方 npm 包 `@earendil-works/pi-coding-agent` 的 `latest` 稳定版本；不把当前手动安装的版本作为固定目标。
- R2. 镜像提供兼容 R1 的 Node.js LTS 与 npm；当前选用 Node.js 24 LTS 的最新补丁版本。
- R3. 普通 `dev` 用户在交互 shell 和非登录 shell 中都能直接调用 `node`、`npm`、`pi`，实际执行镜像中的程序。
- R4. Pi 全局配置、认证数据、会话等保存在宿主项目的 `.container-state/pi/`，绑定到 `/home/dev/.pi`；项目文件继续使用已有的 `/workspace` 绑定挂载。
- R5. 同一容器停启、删除容器后重新挂载同一命名卷，Pi 数据保持不变；首次挂载时 `dev` 可以写入。
- R6. 现有容器中的 Pi 数据须在部署重建前备份并迁入新卷；不得把“挂载新卷”视为自动迁移旧容器可写层。
- R7. 保留现有基础镜像、Rust 与 bubblewrap 安装、非 root 运行用户及其他持久卷；不向镜像或仓库写入真实密钥。
- R8. 文档说明主动更新时怎样刷新 Node 镜像和 Pi 安装层，并记录实际安装版本；普通容器启动不执行联网升级。

“最新”按主动刷新构建时官方发布的稳定版本判断，不承诺已构建镜像会自动随上游更新。当前 Pi `latest` 为 `1.4.0`，要求 Node.js `>=22.19.0`；这只是调研时的结果，不是未来安装版本的固定值。

范围是 Docker 软件安装与数据持久化，不包含模型供应商接入、Pi 插件安装或 Rust 业务功能修改。不新增性能阈值，构建耗时与镜像增量在实现时记录实际结果。

交付范围补充：按用户后续指令，本轮只准备配置并迁移当前数据，不构建镜像或重建容器。迁移采用复制、内容校验及保留旧目录的方式，当前容器通过符号链接继续使用持久目录；镜像与容器生命周期验收留待实际构建后进行。

## 2. 哪些情况容易出错

- 缓存命中 → 普通重建可能复用旧安装层；主动更新必须刷新基础镜像并禁用相关构建缓存。
- 新卷首次挂载 → `dev` 能创建配置和会话文件，不需要以 root 运行 Pi。
- 旧目录含程序启动器 → 数据迁移后 `pi` 仍调用镜像安装的版本，不能命中卷内遗留旧程序。
- 删除并重建容器 → 同一命名卷中的测试配置与会话内容不变；显式删除卷不在保留承诺内。
- 构建需要代理 → 使用 Docker 构建代理参数；Compose 的运行时代理不能作为构建已配置代理的证据。
- 上游提高 Node 要求 → 构建或兼容性检查明确失败，更新配套 LTS 后重验，不忽略不兼容警告交付。

## 3. 重要做法，为什么这样做

软件安装到镜像的系统目录，Pi 数据绑定宿主项目目录。两者分开，避免持久目录遮盖新镜像中的程序。使用现有 `/workspace` 挂载先保存数据，并将当前数据路径链接到该目录，使后续写入立即持久化，不需要现在重建容器。`.container-state/` 已排除在 Git 之外。

使用官方 Node Docker 镜像提供 Node/npm，最终运行镜像仍继承 `agentlab-base:latest`。Pi 使用官网当前 npm 安装方式，并按照官网启用 `--ignore-scripts`。

## 4. 踩过的坑，怎样解决

当前只读检查发现 `pi --version` 为 `1.4.0`，当前 shell 找不到 `node`、`npm`；这不影响按 R1、R2 准备镜像安装步骤，也不能据此断言用户未在其他环境安装过 Node。当前环境没有 Docker CLI 或引擎连接，新增持久目录采用宿主绑定方式，避免保存数据还依赖创建命名卷。实际迁移与检查结果见本功能日志。
