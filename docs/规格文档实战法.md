# 规格文档实战法

## 核心思想

**每个功能写一份说明：做什么、有哪些限制、怎样才算做好。你定要求，AI 写代码，最后按说明检查。**

这份说明就是“规格文档”。代码以后可以重写，要求、做法的理由和踩过的坑都留在文档里。先预测结果，再实际运行，记下差别，既能完成开发，也能积累经验。

## 详细说明

### 文档和代码旁的说明，分开放

- **文档**：记功能要求、重要做法和经验，方便以后重做或换项目使用。
- **代码注释**：写在代码旁，只解释附近代码；改代码时一起更新。

| 内容 | 放哪 |
|---|---|
| 做什么、需要什么、返回什么、有哪些限制 | 第 1 节 |
| 哪些情况容易出错 | 第 2 节 |
| 重要做法及其理由 | 第 3 节 |
| 踩过的坑和解决办法 | 第 4 节 |
| 预计结果、实际结果、是否合格 | 第 5 节 |
| 某几行代码为什么这样写 | 代码注释 |
| 临时草稿 | 有用的内容整理进文档 |

### 一份文档，固定写五节

下面用“每日签到”演示写法，**没有做过真实测试**。把 `【】` 换成项目实际条件和要求，把“待测”换成真实结果。

速度就是等多久能得到结果；资源就是用了多少电脑计算能力、内存、磁盘空间或钱。只写需要限制的项目。没有依据时，先测出当前水平，再确定要求，不随便填数字。

性能数字要写清测法，不能只写“快”。先用最小原型或空跑测一个基线，再留 2–3 倍余量。至少写：p95 还是平均值、多少并发、正式请求多少次、预热几次、跑几轮取哪一轮、机器和版本。换机器或换语言要重新测。压测客户端自身的实现也会明显影响测得的延迟：定阈值前，先用最小回显对照服务器跑同一负载，确认客户端开销远小于阈值；换了客户端实现，同一服务测出的数字不能直接比较。费用也要写清统计范围：只算模型调用，还是也算存储、带宽、人工。分别记“实付 / 估算 / 未测”；实付写金额来源，估算写模型、用量、单价和单价日期。没有数据就写“未测”，不能写成 0。

```markdown
# 规格：每日签到

- 状态：待实现
- 更新时间：【日期】

## 1. 要做什么，有哪些要求
- 功能：每天签到，查询今天是否已签、连续签了几天。
- 输入：用户编号。
- 返回：今天是否已签、连续签到天数。
- 范围：只做签到和查询，不做积分或补签；不改已有用户编号的用法。
- 规则：每人每天只能签到一次，按用户所在地的日期算当天。
- 测试条件：【机器配置】、【系统/语言版本】、【已有记录数量】、【同时请求数量】；服务端和客户端是否分开进程。
- 速度和资源要求：在上述条件下，主要操作 p95 不超过【毫秒】；内存不超过【大小】（写清测哪个进程、什么时候测）；费用不超过【金额及对应时间或次数】。其他限制按需补充。

## 2. 哪些情况容易出错
- 同时点两次签到，会不会重复记录、重复增加天数？
- 用户和运行程序的电脑不在同一地区，会不会算错日期？
- 漏签一天，连续天数会不会从 1 重新算？
- 记录或同时使用的人变多后，会不会变慢、占用过多资源？

## 3. 重要做法，为什么这样做
- 防重复：让数据库（保存记录的地方）限制“同一用户、同一天”只能存一条，避免两个请求都写入。
- 算日期：先算用户所在地的日期，再保存，避免按运行程序的电脑日期算错一天。
- 查天数：保存连续签到天数，查询时直接读，避免每次翻全部历史。签到记录和天数要一起更新，不能只成功一半。

## 4. 踩过的坑，怎样解决
- 遇到问题后，写清“出了什么问题 → 原因 → 怎样解决”。这里先留空，不把猜测当经验。
- 只记这个项目真实发生的坑；能复用到别的项目的，整理进项目的 `project-lessons.md`（如果有），这里留一句指针，不抄两遍。

## 5. 先预测，再实测，最后确认是否合格
- 同时签到两次 → 预计当天只存一条，天数只增加一次 → 实测：待测。
- 用户和运行程序的电脑日期不同 → 预计仍按用户所在地日期记录 → 实测：待测。
- 漏签一天后再签到 → 预计连续天数变成 1 → 实测：待测。
- 在第 1 节约定的条件下运行 → 预计速度和资源占用都不超限 → 实测：待测。
- 验证方法：写一条能直接跑的命令（或点击步骤），固定随机种子和测试数据；输出、截图放 `docs/logs/001-daily-checkin/`。优化前后用相同条件比较，记下机器和版本。
- 验收：实现的人不能自己判“通过”，也没权改最终状态。验收人按本节逐条跑，只依据规格、证据和可运行产物（启动说明）判定；不看实现源码，代码审查另做。
- 完成条件：功能、容易出错的情况、速度和资源要求都检查通过。没测过、要求没定、或只有实现者自己说“通过”的，不能算通过。
```

写第 2 节时，每条尽量写成“什么情况 → 期望什么结果”，验收时才能判过不过。至少覆盖：重复/并发、边界值、非法输入、重启后数据还在不在、数据量变大。时间边界（正好过期、跨时区）和编码边界（中文、空格、已有 `%XX`）最容易漏。

预测错了也有价值：把原因和解决办法记进第 4 节，更新第 5 节的真实结果。

### 怎么交给 AI 实现或重写

把文档交给 AI，说明要用的编程语言和工具。还没选好，可以先让 AI 给建议。

> 按这份规格，用【语言和工具】实现。守住功能要求、特殊情况和资源限制，其余做法自行选择。先保证正确，再解决速度和资源占用不达标的问题，直到所有检查通过。达到要求就结束，不额外增加功能或反复优化。遇到要求冲突或无法验证的地方，说明原因和还缺什么条件。
>
> 不许改规格里的功能、数字和验收条件；发现规格有问题，停下来列出来，不要自己补。做完报告：完成了什么、没做什么、做了哪些假设、证据在哪、和规格有没有偏差。状态先写“待验收”，不要自己写“已通过”。

以后换语言或工具，仍可使用这份说明，但要重新检查功能、速度和资源消耗，不能默认结果一样。

### 交给 AI 前，先自己检查

- 每条要求都能判“过/不过”吗？有没有“快、稳、友好、尽量”这类没法判的词？
- 每个数字都写了测法吗？p95 还是平均值、多少并发、跑几轮、在哪台机器上测。
- 费用写清范围了吗？只算模型调用还是也算存储、带宽；实付、估算、未测分开，缺数据不能写 0。
- 接口写清了吗？输入、输出、状态码、错误情况。
- 边界覆盖了吗？重复/并发、非法输入、边界值、重启、数据量变大、时间和编码。编码类的写清“原样保留”还是“解码后比较”。
- 时间相关的要求，能用短 TTL 等待或可替换时钟测吗？不要靠直接改数据库卡边界。靠等待过期的取样要保证取得到有效样本（例如等到整秒开始再建样本）；快速重试不跨秒，等于只抽一次签。
- 证据放哪、用什么命令跑，写了吗？
- 一份说明是不是只讲一个能独立验收的功能？混进两个就拆。

### 四条提醒

1. **一份说明只讲一个能独立验收的功能：一个明确目标，加一组能各自判过/不过的验收条件。** 篇幅跟着功能走，别为了凑一页删要求；接口多但共用一套约束（同一个数据库、同一组并发要求）时，可以留在一份里，用小节分开。接口数量不设硬上限，能不能拆按验收条件是否独立来判，保留人的判断。
2. **记住问题的原因和解决办法。** 下次换项目，也能少踩同样的坑。
3. **重要变化要更新说明。** 功能表现、限制、重要做法或检查结论变了，文档一起改；只改局部代码细节，不必改规格。
4. **实现和验收分开。** 实现的人只拿冻结的规格和运行约束，最多把状态写成“待验收”；验收的人拿规格、证据和可运行产物（含启动说明），不读实现源码，按证据判“已通过”或“已废弃”。代码审查另做。隔离说明要如实写实现方实际拿到了什么；除规格和运行约束外还拿到材料（如既有测试脚手架）的，不算严格盲测。

## 文档放在哪里

放在项目的 `docs/specs/` 文件夹，和代码一起保存。`docs/index.md` 用来列出每份说明是做什么的。

```
项目文件夹/
├── src/                              # 代码
├── docs/                             # 文档
│   ├── index.md                      # 文档目录
│   ├── specs/                        # 功能说明
│   │   ├── 001-daily-checkin.md       # 每日签到
│   │   ├── 002-user-auth.md           # 用户登录
│   │   └── 003-order-payment.md      # 订单付款
│   └── logs/                         # 验收证据
│       └── 001-daily-checkin/
│           └── 2026-10-24-verify.md
└── README.md                         # 项目介绍
```

文件名用 `编号-功能英文名.md`，不会起英文名可以让 AI 帮忙。**一个功能一份文档**，以后重写哪个功能，就取对应的说明。

每份规格开头写状态和更新时间；每次改动顺手更新日期。状态用“待实现 / 实现中 / 待验收 / 已通过 / 已废弃”，由验收的人改，不要由实现的人自己写“已通过”。验收证据放 `docs/logs/`，按功能分文件夹，文件名带日期，里面记环境、命令、输出和结论。
