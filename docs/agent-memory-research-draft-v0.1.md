# Agent 自动唤起记忆系统：调研与草案 v0.1

日期：2026-11-06

系统根据当前任务和工作阶段，在后台查找记忆，并把符合条件的内容送入 Agent 的下一次模型请求。

本文把“自动涌现”作为使用体验：Agent 无须反复决定是否搜索记忆。程序仍通过检索、筛选和上下文组装完成这个过程。本文不主张该机制等同于人的大脑。

## 一、调研结果

已有开源项目能自动检索并加入上下文。因此，“现有记忆系统都需要 Agent 主动搜索”不准确。需要进一步解决的是：在一个没有新用户消息的长任务中，系统能否根据工作变化，继续送入适用的记忆。

以下结论来自项目的公开文档和部分源码。没有安装这些项目，也没有运行对比测试。表中的限制只针对核对过的路径，不代表项目的全部能力。

| 项目 | 已有机制 | 与本构想的关系及限制 |
| --- | --- | --- |
| [claude-mem](https://github.com/thedotmack/claude-mem) | 自动记录工作并在会话开始时补充历史。可开启按用户消息进行语义匹配的功能；该功能默认关闭。[1][2] | 已有“自动匹配并送入上下文”。核对过的语义路径由用户消息触发；另有读文件前补充历史的路径。尚不能据此认定它能按任意工作阶段持续推送。[3] |
| [claude-supermemory](https://github.com/supermemoryai/claude-supermemory) | 用户提交有实质内容的消息后，程序直接搜索并加入新匹配结果。会话内去重，结束时后台保存新增内容。[4] | 不必等 Agent 调用搜索工具。公开插件采用 Supermemory 服务；不能把插件开源等同于整个后端都可自行部署。 |
| [MemOS](https://github.com/MemTensor/MemOS) | 有后台记忆处理和本地插件。其 DeepSeek Harness 适配器对每个接受的非空用户轮次自动召回一次。[5] | 可以参考其来源标记、去重和超时处理。该适配器明确不因工具消息再次自动召回，所以这条路径没有覆盖长任务中的每一步。 |
| [LangMem](https://github.com/langchain-ai/langmem) | 官方示例在准备模型请求时，由程序搜索记忆并组装上下文；另有后台提取和整理记忆的功能。[6][7] | 已经支持由程序触发读取。示例使用最后一条消息作为查询；本构想需要增加任务、阶段和当前问题的组合线索。 |
| [memU](https://github.com/NevaMind-AI/memU) | 当前主分支的桌面适配器定期处理历史，并通过常驻指令要求 Agent 在回答前执行检索。[8] | 有后台整理，但核对到的读取路径仍依赖 Agent 执行指令。不能只根据早期“proactive”介绍判断当前机制。 |
| [Mem0](https://github.com/mem0ai/mem0) | 提供按含义搜索、范围过滤、阈值和结果数量控制。[9] | 可作为存储和检索组件。其搜索接口本身不决定何时把结果送进某个 Harness。 |

还有一篇非常接近的论文：[Who Schedules Agent Memory? A Sidecar Approach to Long-Horizon Tasks（MemSidecar）](https://arxiv.org/abs/2611.00779)，于 2026-10-31 提交。[10]

论文将记忆调度交给独立模块：Hooks 在执行事件符合条件时直接送入绑定记忆；Foresight 在后台预测查询并预先准备结果，实际查询到来后再交付。前者尤其接近“记忆自己出现”。本次没有确认到作者发布的代码仓库，因此把它列为研究参考，不列为已核实的开源实现。

调研判断：可以继续设计，但应把重点放在“长任务中的触发与交付”。“向量相似度超过阈值”已有成熟组件；“何时检查、依据什么检查、何时送达”才是这里需要定义的行为。

## 二、草案目标

Agent 主要负责完成任务。Harness，即负责调用模型和执行工具的外围程序，负责让适用的记忆及时进入上下文。

第一版假设已经有一批可读取的记忆文档。先验证自动唤起是否有效。自动形成、修订和删除记忆，作为后续工作。

## 三、实际过程

1. **Agent 声明当前关注点。** 开始任务或进入新阶段时，Agent 报告任务目标、当前阶段、当前问题和所需知识。它不必指定记忆文件，也不必等待搜索结果。
2. **Harness 保存并补充线索。** Harness 将关注点与最新用户要求、工具名称、工具参数和简短结果组合。这样，Agent 没有更新关注点时，检索仍能继续。
3. **后台程序查找候选记忆。** 程序先按用户、项目和访问范围过滤，再比较文本含义。语义向量是表示文本含义的一组数字；程序用它计算相似程度。
4. **程序筛选候选内容。** 相似度达到阈值后，程序还检查记忆是否有效、是否已被新版本替代、是否已在上下文中，以及是否超过长度预算。
5. **Harness 排队交付。** 程序把通过检查的内容放入待交付队列。下一次模型调用前，Harness 再检查任务和阶段是否仍匹配，然后加入上下文。
6. **Agent 使用收到的资料继续工作。** 记忆随正常请求一起到达。Agent 不需要再打开文件，才能看到被选中的内容。

关注点可以用以下结构表达。这是概念示例，不是已确定的接口：

```json
{
  "task_id": "task-17",
  "focus_version": 3,
  "goal": "修复后台任务退出后仍占用资源的问题",
  "phase": "验证",
  "current_problem": "检查停止后是否仍有子进程",
  "knowledge_needs": ["历史故障原因", "验收方法"],
  "entities": ["worker", "进程回收"]
}
```

用户和项目范围由 Harness 的可信会话状态确定。Agent 提交的内容只能缩小检索范围，不能扩大访问权限。

## 四、何时检查

第一版采用事件触发，不持续重复计算同一个查询。

| 事件 | Harness 的动作 |
| --- | --- |
| 新任务开始，或用户改变要求 | 保存新任务状态，启动检索 |
| Agent 更新关注点 | 增加关注点版本，启动检索 |
| 一个工具批次结束 | 用本次工具和结果更新线索，启动或合并检索 |
| 记忆文档新增或修订 | 标记索引版本变化，在下一个执行检查点重新匹配 |
| 上下文压缩完成 | 检查哪些已送入的记忆仍被保留；必要时重新送入 |

同一状态下的重复事件要合并。新的任务或关注点版本到来后，取消旧检索，或在交付前丢弃旧结果。工具输出很长时，只选与当前问题有关的短片段。

这个安排减少对 Agent 主动搜索的依赖，但不能保证程序总能准确理解阶段。需要通过任务测试确认其效果。

## 五、何时加入上下文

后台检索可以与 Agent 工作同时进行。结果只能影响后续模型请求，不能改写已经发送的请求，也不能改变正在生成中的模型内部状态。

Harness 在完整的工具批次结束后、下一次模型调用前交付结果。不要把一组工具调用和对应结果拆开。若本次生成直接结束，则不能保证记忆影响这次回答；下一次请求才会收到它。

普通检索失败或超时时，主任务继续，后续事件可以重试。因此，必须执行的现行规则应通过固定规则通道提供，不能依靠相似度决定是否出现。

## 六、如何承载记忆

Harness 内部应把结果记录为“自动补充的记忆资料”，保留来源和版本。再由各模型适配器转成支持的补充上下文格式。

如果某个接口需要用 `user` 消息承载资料，可以保留这个做法，但必须标明它由 Harness 自动加入。不要让旧资料看起来像用户刚提出的新要求。上层指令应明确：这些内容是历史资料，不能单独授权新动作；与当前要求或现行规则冲突时，按当前要求和现行规则处理。

建议送入一个有长度上限的资料包：

```text
【Harness 自动补充：历史记忆资料】
来源：memory/worker-reaping.md
记忆编号：mem-042；版本：4；更新日期：2026-11-05
适用范围：当前项目的后台进程退出检查

内容：历史故障中，外层进程退出并不代表其子进程已被回收。
验收时需要同时检查子进程是否退出、是否完成等待。
【资料结束】
```

上例内容仅用于说明消息格式。

优先送入能独立理解的相关段落，并带必要上下文。短文档可全文送入；长文档不因其中一个片段命中，就把全文放入。

## 七、最少需要的控制

| 控制 | 原因 |
| --- | --- |
| 先过滤范围，再比较含义 | 不同项目可能使用相同术语 |
| 检查有效状态、适用版本和来源 | 内容相似，不代表内容仍然正确 |
| 按实际仍在上下文中的记忆版本去重 | 避免重复占空间；压缩丢失后又能重新送入 |
| 限制每次资料包和当前有效记忆的总长度 | 避免长任务不断累积记忆内容 |
| 每次交付前核对任务与关注点版本 | 避免后台旧结果进入已经变化的工作阶段 |
| 记录送入原因和使用反馈 | 便于查明漏送、误送和重复送入的原因 |

相似度阈值需要用选定的文本向量模型和真实样本校准。不能把一个固定数字当作通用标准。相似度也不是“正确概率”。

例如：假设一次试验设置阈值为 0.80，一条记忆得分 0.84，它可以进入候选集；如果该记忆已失效，程序仍应丢弃。这里的数字只说明筛选过程，不是建议默认值。

## 八、第一版范围与验证

第一版采用已有 Markdown 文档、一个文本向量模型、一个本地索引和一个后台队列。先支持单 Agent、单项目。暂不加入知识图谱、多 Agent 协同或自动改写记忆。

每次最多送入 3 条记忆，总长最多 1,000 tokens，作为首轮试验预算；tokens 是模型计量文本长度的单位。这些数值需要根据测试调整。还应限制当前有效记忆的累计长度，并在过期、阶段变化或预算不足时撤下旧内容。

用相同模型、相同任务和相同记忆，比较三种方式：Agent 主动搜索、只在新用户消息时自动搜索、按任务执行事件自动搜索。

| 测试 | 要确认的行为 |
| --- | --- |
| 用户不再发消息，Agent 连续执行 30 个工具步骤 | 后续步骤仍能触发相关记忆交付 |
| Agent 从排查进入验证，但没有更新关注点 | 最新工具结果仍能改变候选记忆 |
| 两个项目有相似文档 | 只送入有权读取且属于当前范围的内容 |
| 后台返回时，任务已经切换 | 丢弃旧任务结果 |
| 记忆已失效，或同一版本仍在上下文中 | 不送入失效内容，不重复送入已有内容 |
| 上下文压缩移除了适用记忆 | 后续检查点可以重新送入 |
| 检索服务不可用 | 普通工作继续，错误可查 |

记录四类结果：需要的记忆是否及时出现、送入内容是否适用、任务是否更容易完成、额外时间和文本用量是多少。“成功加入消息”只证明交付完成，不能证明 Agent 使用了记忆。

这份草案先验证一个问题：当 Agent 长时间工作且不主动搜索记忆时，Harness 能否在有用的时点，把少量适用资料送到它面前。
