# 027 访问边界实测（2026-10-26）——终态：阻断

实测（推翻预设）：
- sudo -n true：可用；sudo -l：`User dev may run (ALL) NOPASSWD: ALL`（/etc/sudoers root 0400，授权来自容器基础配置）。
- su：拒绝（无 root 口令）；doas：不存在。setuid 共 11 个标准系统工具，无自装异常项。
- 假凭据 0600 文件：Agent Shell 直接可读（同 UID 无强制边界，符合预期）。
- ZCode 快照范围（2025 个 artifact 的 path 前缀统计）：/workspace 1849、/tmp 122、/vault 43、/home 11
  ——不限于工作区，"迁移到某安全路径"无实测依据。

成熟机制评估（.env 原位约束下）：
- root 属主 0400/0440：应用同以 dev 运行，不可读（0440 组可读则 Agent 同组也可读）——不可行。
- 独立 UID 服务化运行：dev 可 NOPASSWD sudo 成任意 UID，仍挡不住；NOPASSWD: ALL 使一切针对 dev 的
  进程/文件边界可被旁路。
- 容器拆分（Agent 容器不挂载凭据卷）＋宿主 Windows ACL（9p 层）：唯一有效方向，均属管理员级环境变更。

阻断结论：当前权限模型（dev≈root、应用与 Agent 同 UID）下无法实现"Agent 不可读、应用可读"的强制限制。
所需管理员操作（待决定）：①收紧 sudoers（限定命令或要求口令）；②多容器/多用户拆分使 Agent 侧不挂载
模型凭据；③宿主层 Windows ACL。影响：①③影响日常调试便利；②需改 compose 与运行方式；回滚＝恢复
sudoers/compose/ACL 原状。已落地替代缓解：025 脱敏、026 提交扫描、AGENTS.md F7 审计与流程约定（非强制）。
