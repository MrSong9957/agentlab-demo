# 流式输出简明技术规范（第二部分）

日期：2026-11-02。
适用：流式输出功能。计划暂定编号 039。范围：API 层与宿主层改动。
前接：[SSE 事件类型简明规范](2026-11-02-039-stream-sse-event-types.md)。
标准：ASD-STE100 中文近似，约 80% 达标。

## 1. 改动总则

- 改动只改一件事：读的节奏。
- 现状是“攒齐再拆”。改后是“读一块、拆一事件”。
- 不重写协议组装规则。复用 SSE 语法解析器。新增按块喂入的增量入口。现有整段入口保留，用于非流式和测试。
- 提交边界不变。完成事件前，只显示，不保存。

## 2. API 层：有界增量读取

- 程序读到一块字节。程序立刻交给解码器。
- 解码器吐出 0 条或多条完整事件。程序处理事件。程序再读下一块。
- 循环体每步都过闸门。

### 2.1 四道闸门

| 闸门 | 作用 |
|---|---|
| 总字节上限 | 超限即停。报错。同时约束原始流字节和组装结果。 |
| 总时限 | 超时即停。报错。 |
| 取消检查 | 用户中断即停。阻塞读要可中断。 |
| 错误分类 | 断流、坏数据按类走失败路径。 |

### 2.2 解码器喂法

- 现状：整块喂完，一次拿回全部事件。
- 改后：来一块喂一块。解码器跨块拼接。凑齐 `\n\n` 结束标记就吐一条事件。
- 解码器带状态跨块工作。半个空行不交出事件。
- 协议组装规则不变。增量入口一边产出显示事件，一边攒出完整组装结果。

### 2.3 事件分流

- 文本片段 → 立刻送往宿主，喂显示。同一文本进入最终文本组装器。
- 工具参数片段 → 只累积，不进可见文本。
- 完成事件 → 触发本请求提交。先保存 assistant 记录。有工具调用时运行工具。
- 终止：收到完成事件，或闸门拦下，或出错。

### 2.4 硬边界

- 流式显示不是提交。
- 边读边显示，但历史只在完成后写。
- 保存的文本必须等于完成时的组装文本。

## 3. 宿主层：流式事件通道

### 3.1 现状

- API 不流式。用户轮同步运行。
- 宿主卡在原地等成品。
- [tui_host.rs:813](../../src/app/src/tui_host.rs#L813) 是当前唯一发送显示事件处。因为手里只有完整回复。
- CLI 在完整回复后打印 `Agent：{reply}`。

### 3.2 改动

- 在宿主中增加流式事件通道。
- API 层每拆出一条事件，放入通道。宿主从通道取出。
- 事件流用于显示。完整组装结果仍返回宿主，用于保存和运行工具。
- 通道承载三类事件。

```text
api 层 ──事件──> [流式事件通道] ──> 宿主分发 ──> TUI
                                          └──> CLI
```

### 3.3 TUI：接线，不造件

| 通道来的事件 | 宿主动作 | 复用零件 |
|---|---|---|
| 文本片段 | 转 `Delta`。逐条发往显示。 | `Delta` 和 markdown 流式渲染 |
| 工具参数片段 | 只累积。 | 无显示动作 |
| 本请求完成事件 | 保存 assistant 记录。有工具调用时继续本轮。 | 006 工具循环 |
| 最终回复完成 | 发 `Final`。结束本轮。 | `Final` |
| 用户取消 | 走取消链路。 | 已有取消链路 |

- 只改节奏。从批量连发改为来一段发一条。
- 工具批次中间不发 `Final`。`Final` 只在最终回复结束时发。

### 3.4 CLI：两模式分道

- 终端模式：来一段打印一段。
- 管道或非终端模式：按 001 契约保持现状。不增量。
- 流中取消时，CLI 必须保持存活。
- 中断的是读取和提交，不是进程。

## 4. 收拢

> 两层各改一件事。
> API 层：把“读完整响应体”换成“读一块、过闸门、拆事件、分流”。
> 宿主层：在 API 与显示之间架一条流式事件通道。按事件路由到 TUI 和 CLI。
> 解码器、渲染器、取消链路、提交边界，全部复用或保持。

## 5. 与现有实现的核对

2026-11-02 核对现有代码和契约。共有四处原表述需要校正。

- 原句“解码器不重写”需要校正。改为“不重写协议组装规则”。新增增量入口。保留整段入口。现状 [api/stream.rs:5](../../src/app/src/api/stream.rs#L5) 的 `decode` 只接收整段文本。[api.rs:363](../../src/app/src/api.rs#L363) 先读取完整响应体。
- 原句“宿主与 API 之间从返回值换成事件流”需要校正。事件流用于显示。完整组装结果仍返回宿主。提交需要完整结果。[turn.rs:2010](../../src/app/src/turn.rs#L2010) 和 [turn.rs:2021](../../src/app/src/turn.rs#L2021) 依赖完整 assistant 记录。
- 原句“完成事件 → 发 `Final`”需要校正。本请求完成事件先提交。只有最终回复完成才发 `Final`。工具批次会继续本轮。[turn.rs:2025](../../src/app/src/turn.rs#L2025) 起按批执行工具。
- 原句“文本片段 → 立刻送往宿主，喂显示”需要校正。文本片段同时进入显示端和最终文本组装器。保存需要完整文本。
- 现状 [tui_host.rs:822](../../src/app/src/tui_host.rs#L822) 的 `Final` 在整轮结束后发送。流式改造后仍保持“最终回复才发 `Final`”。
- 现状 [api.rs:363](../../src/app/src/api.rs#L363) 的 `read_limited_string` 一次性读取。增量路径必须重做字节计数、总时限和取消检查。

## 6. 风险与待决

- 阻塞读的取消。ureq 的阻塞读不一定响应取消标志。实现要用短读循环、超时或可中断 IO。不能只在循环头检查。
- `Delta` 分片。现有 `Delta` 可接收任意文本。markdown 渲染要用现有 controller 测半行、半代码块和表格。
- 总时限。单次 IO 超时不能代替总时限。要设墙钟 deadline。
- 完成事件判定。五个协议的结束标记不同。每个协议要有测试。
- 工具批次与最终回复。宿主必须区分“本请求完成”和“本轮结束”。
- 取消后的显示文本保留或清除。沿用第一部分待决项。
- 请求级重试（040）与本通道的边界。流式文本可见后不重试。
