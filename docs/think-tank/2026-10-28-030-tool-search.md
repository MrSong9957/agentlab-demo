# 030 工具搜索：计划前调研与复核

- 日期：2026-10-28；倒序调研第 4/6 项，在 031 复核后启动。
- 目标：让按需加载减少固定夹具的完整请求字节，同时保持确定性命中和请求级调用资格。
- 输入：[030 规格与计划](../specs/030-tool-search.md)、当前 MCP 快照/请求组装/工具分派；三位独立专家及 last30days 侦察兵。
- 结论：**补充 M0/M1 的同分截断验证；保留 M2–M5 已充分约定的资格、协议与性能测法**。本轮未跑搜索原型或性能测试。

## 共识

目录可搜索不等于工具可调用；执行资格只来自产生当前响应的请求声明。下一请求加载、同批不升级、取消不迟到发布、恢复不激活及五协议完整定义仍按原计划。2048 项目录、128 项声明和最终请求字节是不同边界，分别验证。

## 冲突与裁决

三位专家没有互斥方案。检索专家指出固定版本 [bm25 scorer 源码](https://docs.rs/bm25/2.3.2/src/bm25/scorer.rs.html#95)按分数排序，不替项目实现同分身份顺序。若先取库返回的 limit 项，再排同分，跨截断边界的候选已丢失。M1 因此要在完整正分候选上完成既定二次排序，再截断；M0 加目录重排且同分超过 limit 的夹具。

性能专家认可原 §1.6 的完整请求计量和三轮测法，协议专家认可 M3/M4 的执行集合与原生状态约束。保留这些计划，不增加全局缓存、语义检索或新的身份发现能力。

## 社区校准

HN/GitHub quick 引擎实际运行 3.6 秒、退出 0，两源各返回 6 个原始项；形成的四簇均为泛搜索、认证或 UI 话题，未作为本项证据。原生搜索补充的 [Aixy 第一方复盘](https://aixy-gateway.com/blog/mcp-tool-discovery-context/)（10 月 7 日）记录了目录挤占初始上下文，以及搜中工具后仍缺身份/工作区的问题。它使用合成输入和固定成功步骤，未测真实误调用、模型行为、缓存或账单，不能据此给本项目填写收益比例。

[OpenAI 官方协议文档](https://developers.openai.com/api/docs/guides/tools-tool-search)仅用于区分原生 typed 搜索与本项目普通函数适配，不当作近期社区实证。近期直接样本不足以称共识；旧讨论和不相关命中已排除，详见来源及真实运行记录。

## 组合方案与计划文档检查

| 优先级 | 落点 | 修订与验证 |
|---|---|---|
| 1 | M0 | 在原固定词法夹具中加入同分项跨 limit、目录重排；预期名单与顺序须一致。 |
| 2 | M1 | 正分候选先按分数及原始身份排定，再取 limit；不以库的预截断结果补排序。 |
| 3 | M3/M4 | 保留请求快照门禁、下一请求声明、五协议 Schema/ID/原生状态及真实 MCP 调用计数。 |
| 4 | M0/M5 | 保留完整出站请求含搜索历史的计量、96→0→2 夹具及 p95/RSS 冻结；未实测不填通过。 |

§1、§2、§5 保持不变，门禁入口对齐现行 AGENTS。专家所述目标均为后续验证要求，不是本轮性能结果。

## 背景知识

稳定排序必须覆盖截断之前的候选集合；仅稳定排列已截断子集不能保证命中名单稳定。首次少发 Schema，也不保证完成任务时的完整请求更小，新增搜索历史须一起计量。
