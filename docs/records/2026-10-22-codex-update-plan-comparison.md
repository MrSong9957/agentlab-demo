## 结论

原表「缺少，适合补充」的判断成立，建议近期补充。它能把多步骤任务的当前步骤和完成状态直接展示给用户，后端逻辑较少，不要求迁移 Chat Completions 或引入外部服务。完整交付仍需覆盖提示词、工具循环、行式 CLI、TUI 和会话恢复，不能只增加一个工具名称或成功回复。

`update_plan` 是 TODO 清单工具，参数由步骤、状态和可选说明组成。[官方工具定义与使用指引](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide)

按固定提交的处理器实现，模型提交步骤及状态，宿主解析并发布展示事件；它不负责执行步骤、自动调度任务或验证工作是否完成，`completed` 代表模型声明的状态。它也不是 Plan Mode，该版本在 Plan Mode 中明确拒绝调用它。

## Codex 的实际契约

| 项目 | 固定版本行为 | 对本项目的意义 |
|---|---|---|
| 参数 | 必填 `plan` 数组，每项含 `step` 字符串和 `status`；可选 `explanation` | 可直接适配为现有 function 工具，无需自由文本或新 API 协议 |
| 状态 | `pending / in_progress / completed` 三个枚举值 | 保留上游命名；不擅自增加 blocked、cancelled 等新状态 |
| 更新方式 | 每次提交完整步骤列表；参数没有步骤 ID 或局部修改操作 | 最小实现展示每次提交的完整快照，无需新建增量同步机制 |
| 执行 | 反序列化参数，发出 `PlanUpdate(args)` 事件；正常返回文本 `Plan updated` | 计划内容通过事件展示；成功确认本身不包含步骤。应适配本地 JSON 工具结果约定 |
| 校验 | Serde 拒绝未知字段、缺字段和非法状态；「至多一个 in_progress」写在描述里，处理器没有显式计数校验；数组没有最小长度限制 | 若本地要求强制单个进行中、拒绝空步骤或约定空列表清空，应在规格和校验中明确，不能误认为上游已保证 |
| 展示 | `PlanUpdateCell` 按状态呈现清单，可带说明和完成数量 | 优先复用其清单渲染部分，适配本地宿主事件；无需一并移植 Proposed Plan 流式展示或 Plan Mode |

## 本项目的实际缺口

1. **工具不可调用。** [prompt.rs](../../src/app/src/prompt.rs) 用户轮只声明 `exec_command / apply_patch / write_stdin`；[turn.rs](../../src/app/src/turn.rs) 也只有这三项执行分派，`update_plan` 会走未知工具错误。内部记忆合并轮是另一组受限工具，不应顺带开放计划工具。
2. **计划指引被主动移除。** `sent_instructions()` 调用 `without_update_plan_instructions()`；[005 规格](../specs/005-minimal-prompt-assembly.md)要求剔除未开放工具指引，[请求组装测试](../../src/app/tests/prompt_assembly.rs)也断言没有 `update_plan`、用户轮工具恰三项。启用时须同步修订这些契约，保留嵌入母本不改。
3. **TUI 遗留文件不等于已有功能。** [history_cell/mod.rs](../../src/tui/src/history_cell/mod.rs) 中计划类型导入已标为 `008-TRIM`；[对应测试](../../src/tui/src/history_cell/tests.rs)说明 `new_plan_update` 和计划 cell 因无本地事件源被裁掉。虽然还留有计划快照文件，[chat_driver.rs](../../src/tui/src/chat_driver.rs) 的宿主历史类型目前只有 Text、Exec、Patch。
4. **行式与恢复路径均需接通。** [main.rs](../../src/app/src/main.rs) 当前主要显示工具开始活动行，结束通知仅额外显示进程生命周期状态；[tui_host.rs](../../src/app/src/tui_host.rs) 的 `tool_end_item` 只投影 exec/write_stdin/patch。仅让后端返回成功，用户仍看不到结构化计划。

## 建议的最小接入范围

- **定义与分派**：复用上游参数结构、状态枚举和 Schema，加入用户轮工具面；沿用现有调用 ID 配对、参数错误回传与取消规则。成功返回本地 JSON 确认，失败返回错误；具体结果字段由实施规格确定。
- **提示词**：工具接通后恢复相应计划指引；简单任务可以跳过，多步骤任务按实际进展更新。模型标记完成前仍需按任务要求验证。
- **展示**：行式 CLI 输出步骤与状态，TUI 复用上游计划 cell 的必要渲染逻辑；首版可在对话历史中展示各次更新快照，无需额外设计固定侧栏或交互式任务管理器。
- **保存与恢复**：优先使用现有 `AssistantToolCalls` 的原始参数和配对 `ToolResult`，从成功调用重建同一展示投影，不新增独立计划数据库。失败、取消或结果未知的调用不能仅凭参数恢复为已生效计划。现有持久化 `ToolDisplay` 是枚举，添加新变体会影响旧版本读取，需专门评估，不能直接宣称向后兼容；首版可避免新增该持久化变体。
- **循环额度**：[006 规格](../specs/006-tool-call-loop.md)每用户轮最多 8 次模型请求，当前所有工具调用都走相同循环。计划更新若单独形成一轮调用，会占用一次请求额度；应验收包含执行与计划更新的典型流程。任何豁免计划调用或提高上限的方案，都属于另需明确的契约变更。

应同步核对 005（工具与提示词）、006（分派、回传、取消和额度）、007（会话兼容）及 012（实时与恢复展示一致）对应边界；本次未修改这些已验收规格。

## 后续实施的关键验收点

- 本地 mock 驱动真实工具循环：创建计划、更新步骤、全部完成；捕获后续请求，核对参数与调用 ID 保留、结果配对以及内部记忆轮拒绝该工具。
- 非法 JSON、未知字段、非法状态等无效输入被拒绝；空计划、空步骤及多项进行中按 017 保留 Codex 的实际接受行为，不额外加严；旧的有效计划不被失败调用替换。
- 行式真实 CLI 与 TUI 伪终端验收：用户能看见步骤和三种状态，中文、换行、窄屏换行及终端控制字符经过现有显示边界处理；实时与恢复视图一致。
- 保存后恢复只展示成功更新，不重新执行工具；缺失结果、取消、参数错误与旧会话均按约定处理。
- 计划更新与实际执行混合时验证 8 次请求边界，额度耗尽不伪造全部完成。关键回归须证明能检出错误，再按项目要求完成后续测试流程。
